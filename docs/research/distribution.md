# Distributing voz without Gatekeeper friction

Research date: 2026-10-17. Scope: how a self-signed, non-notarized macOS app distributed via GitHub Releases and updated with Sparkle 2 can reach non-technical users without the "Apple could not verify" dialog, with and without a paid Apple Developer Program membership.

Unverified claims are marked **[unverified]**. Every other claim has a source link.

## 1. How Gatekeeper actually works

### The quarantine attribute

Gatekeeper only runs its full check on files that carry the `com.apple.quarantine` extended attribute. Apps opt into setting this attribute on downloads by setting `LSFileQuarantineEnabled` in their `Info.plist`. Browsers do this. Command-line tools that don't request it, such as curl and wget, do not set it ([Unit 42, Gatekeeper bypass research](https://unit42.paloaltonetworks.com/?p=137110); [Eclectic Light, xattr: com.apple.quarantine](https://eclecticlight.co/2017/12/11/xattr-com-apple-quarantine-the-quarantine-flag/)).

Practical effect for voz:

- Browser download of a zip or dmg: quarantined. Gatekeeper checks it on first launch.
- AirDrop, Messages, Mail attachments: these apps also set `LSFileQuarantineEnabled`, so downloads through them are quarantined too ([Eclectic Light, Quarantine: Documents](https://eclecticlight.co/2019/04/26/%F0%9F%8E%97-quarantine-documents/)).
- `curl` to download a release asset: not quarantined. Gatekeeper's download check never fires.
- `git clone` or `swift build` from source: not quarantined, same reasoning, no quarantine-aware app touched the file.
- Homebrew: Homebrew deliberately re-applies the quarantine attribute to cask-installed apps even though its own downloader (curl-based) wouldn't normally set it, specifically so Gatekeeper still checks the binary ([Homebrew/brew#4656, cited in community discussion](https://github.com/caskroom/homebrew-cask/issues/22388)). The `--no-quarantine` flag existed to suppress that re-application.

### App Translocation

Separate from quarantine-triggered signature checks, "App Translocation" (internally called Gatekeeper path randomization) runs a newly downloaded `.app` from a randomized read-only location instead of where the user put it, to stop it loading sibling files from a spoofed path. It triggers when all three are true: the app has the quarantine xattr, it's launched via Launch Services (e.g., double-click in Finder), and Finder hasn't moved it yet. Moving the app with Finder (not `mv` in Terminal) ends translocation ascribed to this mechanism ([Apple Developer Forums](https://developer.apple.com/forums/thread/724969); [analysis cited on mjtsai.com](https://mjtsai.com/blog/?p=14842)). It breaks launch-at-login and self-replacement (relevant to Sparkle) if the app is run straight from a quarantined, un-moved location, another reason to tell users to drag the app to `/Applications`, which voz's `scripts/install.sh` already effectively does when run locally, but a first-time end user dragging the zip's `.app` to Applications via Finder also clears translocation.

### The macOS Sequoia change

Through macOS 14, a user could Control-click (right-click) an unidentified-developer app and choose Open to bypass the dialog immediately, on the first try. macOS Sequoia (15) removed that override. Apple's own release note, as quoted by Michael Tsai: "users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized" ([mjtsai.com, July 2024](https://mjtsai.com/blog/?p=43993)). The replacement path is System Settings > Privacy & Security > scroll down > Open Anyway, confirmed again with Open, as Apple documents in its own support article ([Apple Support, "Open a Mac app from an unidentified developer"](https://support.apple.com/en-us/102445)). That article is written generically for "macOS Catalina and later" and does not call out Sequoia or macOS 26 by name, but its screenshots are Sequoia-era and nothing in the current wording restores the old one-step Control-click flow. `sudo spctl --global-disable` also stopped working as an IT shortcut in Sequoia ([Cult of Mac](https://www.cultofmac.com/864843/macos-sequoia-removes-handy-shortcut-bypass-gatekeeper-security/)).

### macOS 26 (Tahoe)

I found no macOS 26 change to the Gatekeeper user flow itself. The one concrete macOS 26 Gatekeeper item is a security fix: CVE-2025-46291, a logic bug that let a local app skip Gatekeeper checks, fixed in macOS 26.2 (shipped 2025-12-17) ([SentinelOne CVE database](https://www.sentinelone.com/vulnerability-database/cve-2025-46291/)). This is a vulnerability patch, not a policy or UX change, and it doesn't add friction for a legitimately unsigned app, it closes a bypass. I did not find an Apple changelog entry describing a new Gatekeeper prompt or flow specific to macOS 26; the System Settings > Open Anyway path from Sequoia appears to still be current. **[unverified beyond this]**, if you need certainty for macOS 26.x specifically, check the current wording of support.apple.com/en-us/102445 on a macOS 26 machine, since Apple edits that article in place without a visible version history.

## 3. Getting Developer ID cheaply or free

- **Standard price:** Apple Developer Program membership is $99/year (or local-currency equivalent), unchanged in 2026, required for both individual and organization enrollment and for Developer ID issuance ([aggregated 2026 pricing coverage](https://ambsandigital.com/?p=11104); price not independently confirmed on developer.apple.com in this research pass, treat as high-confidence secondary, not primary).
- **Fee waiver eligibility ([Apple, Membership fee waiver](https://developer.apple.com/support/membership-fee-waiver/)):**
  - Eligible entity types: nonprofit organizations (recognized by a relevant authority, e.g. IRS in the US), accredited educational institutions, and government entities.
  - Must be a legal entity, individuals, sole proprietors, and single-person businesses do **not** qualify.
  - Must not have signed the Paid Applications Agreement and must not sell digital goods/services through any app.
  - No country list is published; eligibility is evaluated against whatever accreditation/registration authority exists in the applicant's own region.
  - Apply during enrollment, or at any time before an existing membership expires, via Apple's fee waiver request form.
  - This path does not fit voz as currently structured: a solo-developer project isn't a nonprofit, school, or government entity, and incorporating a nonprofit solely to get a free certificate is disproportionate.
- **Joining an existing team:** Only an **Account Holder** (and the page implies Admins have lesser standing on this specific capability, the Apple page states the Account Holder role, not Admin, is required to generate the Developer ID certificate) can create Developer ID Application certificates for a team ([Apple, Developer ID](https://developer.apple.com/developer-id/)). Joining someone else's paid team as a member doesn't give you your own signing identity under your own name; it gives you access to sign under their team ID, which raises its own trust questions for a product named and owned by you.
- **Individual vs organization enrollment:** both cost $99/year and grant identical technical capability (Developer ID issuance, notarization). Organization accounts additionally support multiple named members with roles; individual accounts are single-owner. Neither is cheaper than the other, the distinction only matters for team management and how your name/company appears as the signer ([enrollment comparison, secondary source](https://knowledgebase.getthereferral.com/knowledgebase/individual-and-organization-enrollment-apple-developer-program); not independently confirmed against developer.apple.com's enrollment page in this pass).
- **Third parties that sign open-source apps for free:**
  - **Mac Admins Open Source (MAOS)**, run by the Mac Admins Foundation, provides free Developer ID signing to vetted open-source Mac admin tools, after a review of the repo's security, coding practices, and maintenance plan ([Mac Admins Foundation news, cited via macadmins.org](https://macadmins.org/news/tag/Programs)). This dates to roughly 2023; I could not confirm it's still accepting new projects in 2026, and it's explicitly scoped to Mac-admin-category tools, which voz (a dictation app) likely isn't. **[unverified current status]**
  - Some solo maintainers fund their own $99/year membership through GitHub Sponsors or similar (e.g. ungoogled-chromium-macos) ([project release notes, cited via newreleases.io](https://newreleases.io/project/github/ungoogled-software/ungoogled-chromium-macos/release/150.0.7871.46-1.1)). This is just "pay the $99 yourself, optionally reimbursed by donations," not a separate free program.
  - I found no general-purpose free code-signing foundation for macOS apps analogous to what exists for some Windows/Linux ecosystems. **[unverified / likely does not exist]**

## 4. What Developer ID + notarization actually buys you

- With a Developer ID certificate, the hardened runtime, and a stapled notarization ticket, a downloaded zip or dmg opens with only the normal "this app was downloaded from the internet, are you sure you want to open it?" confirmation, the Gatekeeper "cannot verify / cannot check for malicious software" block does not appear, because Gatekeeper's quarantine-triggered check now finds a valid signature plus a notarization ticket ([Apple, Developer ID](https://developer.apple.com/developer-id/); [Apple, "Safely open apps," context via support.apple.com/102445](https://support.apple.com/en-us/102445)).
- The one-time "are you sure" confirm after first launch is standard Gatekeeper behavior for any downloaded, quarantined, properly-signed app and is not something Apple provides an API or entitlement to skip, it is the intended minimum friction, separate from the "could not verify" rejection dialog. I found no documented way to suppress it outside MDM-managed devices.
- Zip files cannot carry a staple directly; the standard flow is: sign everything (including Sparkle's bundled helper binaries, a documented historical failure point, see below) → zip with `ditto` → notarize the zip → unzip → staple the `.app` → re-zip with `ditto` for distribution ([developer workflow notes, secondary source](https://zenn.dev/iseebi/articles/macos_sparkle_spm_ci_notarization_issue); consistent with Apple's documented stapler usage on dmg/pkg in [Developer ID page](https://developer.apple.com/developer-id/)).
- Sparkle's own documentation explicitly recommends Developer ID signing plus hardened runtime for distribution and warns that Library Validation (required for notarization) will block loading Sparkle.framework unless it's properly signed, exactly the entitlement (`com.apple.security.cs.disable-library-validation`) voz's `docs/releasing.md` already documents as a stopgap for the self-signed identity, to be removed once on Developer ID ([Sparkle docs](https://sparkle-project.org/documentation/); corroborated by voz's own `docs/releasing.md` lines 73–78).

## 5. What comparable unsigned/paid-free open source menu bar apps do

- **Ice** (menu bar icon manager): ships a Homebrew cask, but at least one user on macOS Tahoe had to manually run `sudo xattr -dr com.apple.quarantine /Applications/Ice.app` to resolve a Gatekeeper-related issue post-install ([GitHub issue](https://github.com/jordanbaird/Ice/issues/711)), consistent with "Homebrew cask" alone not being a guaranteed bypass once Gatekeeper checks fire.
- **IceMelt** (a fork of Ice): advertises itself specifically as Developer-ID-signed and notarized, so it "opens without a Gatekeeper override," contrasted explicitly against the original project ([IceMelt repo description, as summarized in search](https://github.com/pnikolaidis/icemelt)), a direct example of a maintainer paying for Developer ID specifically to remove this friction for users.
- **Mini vMac**, a long-running unsigned hobby project, documents the `xattr -cr <dragged-app-path>` Terminal workaround directly in its install instructions, with an explicit warning to only do this for apps you trust ([gryphel.com/Mini vMac notes](https://www.gryphel.com/c/minivmac/osx_note.html)), this is the closest real-world analog to "tell users to run one Terminal command," the free fallback most unsigned hobby Mac software converges on.
- I could not confirm from primary README text whether AltTab or Rectangle (both popular free menu bar utilities) are Developer-ID-signed; their GitHub Releases pages would confirm this directly but weren't fetched in this pass. **[unverified]**

## Recommendation

**Zero-friction path:** pay for the $99/year Apple Developer Program as an individual, get a Developer ID Application certificate, notarize and staple every release (zip/dmg), and keep the self-signed CI path as a fallback only until the Developer ID pipeline is verified end to end, this matches the "Add notarization later" section already written into `docs/releasing.md`, which only needs secrets added and the disable-library-validation entitlement removed once Sparkle and all frameworks are also signed with the new identity. No free program (fee waiver, MAOS, third-party signing) realistically fits a solo-maintained dictation app; the waiver requires nonprofit/school/government status, and MAOS is scoped to Mac-admin tooling and of uncertain 2026 availability. $99/year is the actual floor.

**Free fallback, if voz stays unsigned:** ship the zip via GitHub Releases as today, and add one Terminal command to the README/installer output: `xattr -cr /Applications/voz.app` after the user drags the app to Applications. This is the standard unsigned-hobby-app pattern (Mini vMac does exactly this). Do not route this through Homebrew's official tap, Homebrew's own September 2026 policy already disables unsigned casks there, and a third-party tap doesn't remove the underlying quarantine prompt anyway, so it adds a dependency without removing the friction it's meant to solve. A curl-based install script also avoids the dialog on first install, but trains users to pipe a remote script into their shell, which is a worse trust model than the dialog it replaces, use it only if the alternative is literally this README command, and say so plainly rather than hiding it as "easier."

**Migration risk for existing installs:** `docs/releasing.md` already flags this correctly, switching signing identity breaks two things macOS binds to the old identity: microphone/Accessibility permission grants (every user re-prompted after the first Developer-ID-signed update) and the `SMAppService` launch agent (launchd may refuse the new binary's signature, logging "Launch agent did not start," leaving voz running unmanaged until relaunched). Treat the first Developer ID release as a breaking update: announce it, and keep the self-signed build path alive in CI until that release is confirmed working for real users, per this repo's own "never break production" rule, don't delete the self-signed signing step until the Developer ID path is proven, not just built.
