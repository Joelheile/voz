# voz stack research

Date: 2026-10-15. Scope: a small, local-first macOS dictation app (push-to-talk on right Cmd, German and English, local STT, local LLM cleanup, local personalization).

Conventions in this document:

- "Unverified" means I could not confirm the claim against a primary source in this pass.
- "Judgment" means my recommendation, not a sourced fact.
- Apple documentation pages were read through the sosumi.ai mirror of developer.apple.com (the original pages need JavaScript). Apple pages that returned 404 or generic text are flagged.
- Reddit and HN are not used as the main evidence. Competitor blog reviews are labeled as such.
- macOS 27 is shipping as of this date (issues cite macOS 27.0 and 27.0.1). Test on 26.x and 27.x.

## 1. App shell: Swift vs Tauri vs Electron

Findings:

- Installer sizes from current releases. Handy (Tauri 2, cross-platform) macOS arm64 dmg is 18 MiB. boring.notch (native) dmg is 9 MiB. VoiceInk (native, bundles Sparkle, mlx-swift-lm and others) dmg is 48 MiB. FluidVoice (native, bundles FluidAudio) dmg is 69 MiB. The Electron 44.7.2 darwin-arm64 runtime zip alone is 124 MiB. Sources: [Handy](https://github.com/cjpais/Handy/releases/tag/v0.9.8), [boring.notch](https://github.com/TheBoredTeam/boring.notch/releases), [VoiceInk](https://github.com/Beingpax/VoiceInk/releases/tag/v2.21), [FluidVoice](https://github.com/altic-dev/FluidVoice/releases/tag/v1.6.11), [Electron](https://github.com/electron/electron/releases/tag/v44.7.2). Models are downloaded separately in all of them, so these sizes exclude models.
- Tauri uses the system WebView (WKWebView on macOS), linked at runtime, so the runtime is not bundled. Each WebView runs as its own process. Source: [Tauri process model](https://v2.tauri.app/concept/process-model/). Tauri's size page gives no numbers and no Electron comparison: [Tauri size](https://v2.tauri.app/concept/size/).
- Wispr Flow is Electron plus a native Swift helper. One user's log analysis lists helper processes at 47 to 65 MiB each, plus a native helper estimated at about 70 MB more. This is one person's measurement: [wensenwu.com](https://wensenwu.com/thoughts/wispr-flow-investigation). A competitor review claims about 800 MB idle (unverified, third party): [getvoibe](https://www.getvoibe.com/resources/wispr-flow-review/). A feature board post says another app used about 3x the memory of VoiceInk: [featurebase](https://shandianshuo.featurebase.app/p/memory-usage-is-too-high).
- Tauri carries specific costs in this app category. Handy fixed a WebKit memory leak caused by overlay mic-level events and a second leak path through IPC ([Handy #1872 lists #1444 and #1447](https://github.com/cjpais/Handy/issues/1872)). Handy needs a separate Rust key library for modifier-only keys, and a `CGEventTap` in that library was implicated in a kernel panic report ([Handy #1827](https://github.com/cjpais/Handy/issues/1827)).
- Native has its own leaks. FluidVoice reports 204 minutes of CPU time in 17 hours idle ([FluidVoice #948](https://github.com/altic-dev/FluidVoice/issues/948)). VoiceInk reports a stuck Sparkle updater leaking memory in `launchservicesd` ([VoiceInk #760](https://github.com/Beingpax/VoiceInk/issues/760)).

Not found (unverified): a primary measurement of idle RAM, cold start time, and hotkey-to-record latency for Swift vs Tauri vs Electron. Measure these in a prototype.

Decision (judgment): native Swift. SpeechAnalyzer, FoundationModels, CoreAudio, AX and CGEvent are all Apple APIs. FluidAudio and WhisperKit are Swift packages. A web shell adds a process boundary for no gain.

## 2. Global hotkey on right Cmd

CGEventTap vs NSEvent global monitor:

- Apple DTS: the `NSEvent` global monitor requires Accessibility. `CGEventTap` requires Input Monitoring. Input Monitoring is available to sandboxed apps. APIs: `CGPreflightListenEventAccess`, `CGRequestListenEventAccess`. Source: [Apple forums 707680](https://developer.apple.com/forums/thread/707680).
- Forum reports disagree on the permission interplay (a `.listenOnly` tap returning nil until Accessibility is granted on macOS 15, Accessibility granted implying no Input Monitoring prompt). Behavior varies by macOS version. Sources: [thread 122492](https://developer.apple.com/forums/thread/122492), [thread 828052](https://developer.apple.com/forums/thread/828052). Test on 26.x and 27.x.
- The global monitor is observe-only and does not fire for your own app's events, so it needs a local monitor too (third-party guide, unverified against Apple docs): [skills.sh](https://www.skills.sh/makgunay/claude-swift-skills/global-hotkeys).
- Apple has not documented `flagsChanged` with `addGlobalMonitorForEvents` (searched, none found).
- VoiceInk uses a session `CGEventTap`, head insert, `.defaultTap`, with `flagsChanged`, `keyDown`, `keyUp` and mouse events, and re-enables the tap on `tapDisabledByTimeout` and `tapDisabledByUserInput`: [ShortcutMonitor.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Shortcuts/Coordination/ShortcutMonitor.swift).
- Use `.listenOnly` unless you must swallow events. voz does not need to swallow right Cmd. Apple's engineer sample uses `.listenOnly` ([thread 707680](https://developer.apple.com/forums/thread/707680)). The reproduction in [thread 844416](https://developer.apple.com/forums/thread/844416) is for `.defaultTap`.

Revocation hang:

- Revoking Accessibility while an active `.defaultTap` exists froze system input on macOS Sequoia and Tahoe in a forum report, with a Feedback filed (FB24619068) and no Apple answer: [Apple forums 844416](https://developer.apple.com/forums/thread/844416). Handy has the same report: [Handy #1281](https://github.com/cjpais/Handy/issues/1281). A commenter proposes polling `AXIsProcessTrusted` and tearing the tap down.
- Taps can be disabled without the callback firing. FluidVoice runs a 30 second health check and reports a dead window in between: [FluidVoice #657](https://github.com/altic-dev/FluidVoice/issues/657).

Hold vs tap and chords:

- A modifier arrives as `flagsChanged`, with no separate up and down event. You infer state from key code and flags. The device-specific right-Cmd bit (`NX_DEVICERCMDKEYMASK`) is from my memory of IOKit headers and is unverified here. VoiceInk reads state "forKeyCode" in `ShortcutMonitor` (line 326).
- False triggers are the known failure. FluidVoice: left Option modifier-only hotkey fires on Shift+Enter ([#688](https://github.com/altic-dev/FluidVoice/issues/688)), and Left Cmd triggers dictation while Right Option is configured ([#675](https://github.com/altic-dev/FluidVoice/issues/675)). OpenWhispr: hold mode misses the key-up and the pill stays until a second tap ([#2659](https://github.com/OpenWhispr/openwhispr/issues/2659)). Wispr Flow: one analysis traces a stuck spacebar to a modifier left in a "down" set after a missed up event ([wensenwu.com](https://wensenwu.com/thoughts/wispr-flow-investigation)).
- VoiceInk has `handleShortcutInterruptions` and `onStandaloneModifierChord`, which cancel a pending modifier-only shortcut when another key arrives.
- Design (judgment): treat right Cmd as pressed only when key code 54 changes and no other key went down. If any `keyDown` arrives while it is held, cancel the pending recording and pass the event through (so Cmd+C and Cmd+Tab keep working). Reset the pressed set on `tapDisabled*`, on sleep and wake, and on app deactivation. Use a hold threshold (for example 200 ms) to separate tap from hold. The threshold is a starting value to tune.

## 3. Audio capture, muting, Bluetooth

Capture:

- `installTap` buffer size is a request. The block can run off the main thread. One tap per bus. Source: [Apple installTap](<https://sosumi.ai/documentation/avfaudio/avaudionode/installtap(onbus:buffersize:format:block:)>). The page also marks this method deprecated and points to `installAudioTap(onBus:bufferSize:format:tapProvider:)`. Check the SDK you build with.
- `AVAudioEngineConfigurationChange` fires when channel count or sample rate changes. The engine stops. Do not deallocate the engine inside the handler. Source: [Apple docs](https://sosumi.ai/documentation/avfaudio/avaudioengineconfigurationchangenotification).
- Stale format after a sample-rate change produced empty WAVs in VoiceInk: [VoiceInk #956](https://github.com/Beingpax/VoiceInk/issues/956). FluidVoice: selecting a microphone broke recording with error -10851 and a 0 Hz engine: [FluidVoice #757](https://github.com/altic-dev/FluidVoice/issues/757).
- First-word loss. VoiceInk: capture starts about 0.5 s after the key, longer after idle, on a Bluetooth headset ([#996](https://github.com/Beingpax/VoiceInk/issues/996)), and about 1 s with a 192 kHz 4-channel device ([#572](https://github.com/Beingpax/VoiceInk/issues/572)). A commenter uses [macos-mic-keepwarm](https://github.com/drewburchfield/macos-mic-keepwarm). Handy: maintainer says the audio stack is still booting and recommends audio feedback as the readiness cue ([#1879](https://github.com/cjpais/Handy/issues/1879)). Handy's always-on mode burns CPU in the resampler and level meter while idle ([#1872](https://github.com/cjpais/Handy/issues/1872)).
- Design (judgment): start capture on key down before any sound or animation. Keep a short pre-roll only if you accept the orange mic indicator while idle. Play the start sound after the first buffer arrives.

Muting system output:

- VoiceInk mutes the default output device through `kAudioDevicePropertyMute` and tracks which devices it muted. Source: [MediaController.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Media/MediaController.swift).
- Failure on USB DACs: the driver returned `noErr` but did not unmute. The restore logic then treated the muted state as user-owned and never unmuted again. About half of recordings left volume at 0: [VoiceInk #640](https://github.com/Beingpax/VoiceInk/issues/640). The reporter's analysis is in the issue body.
- Handy uses AppleScript for mute, and it does nothing on USB audio interfaces ([Handy #998](https://github.com/cjpais/Handy/issues/998)), has a delay ([#642](https://github.com/cjpais/Handy/issues/642)).
- Mute plus a custom start sound caused a loud system alert beep in VoiceInk: [#980](https://github.com/Beingpax/VoiceInk/issues/980).
- Pausing media instead of muting needs MediaRemote, which Apple restricted in macOS 15.4. VoiceInk uses the [mediaremote-adapter](https://github.com/ungive/mediaremote-adapter) workaround, which runs through `/usr/bin/perl`. Superwhisper is said to pause media (stated in Handy #998, unverified).
- Apple's page for `kAudioDevicePropertyMute` gave no scope or element detail in the mirror (unverified). VoiceInk checks `AudioObjectHasProperty` on the main element and falls back to element 0.
- Per-app ducking: I found no public API in this pass (unverified). Core Audio process taps exist on newer macOS but I did not verify them.
- Crash restore: none of the apps document it (unverified). Design (judgment): write a "voz muted device X" marker to disk before muting, delete it after a verified unmute (read the property back), and on launch restore any leftover marker. Do not infer "user muted" from a muted state at record start without checking the marker. If mute does not read back as set, use volume scalar, then skip.

Bluetooth HFP:

- Bluetooth headsets switch from high-quality playback to a two-way profile when their mic is active, which lowers playback quality and volume. Handy documented this in the README after [#1885](https://github.com/cjpais/Handy/issues/1885).
- Handy PR 1146 prefers non-Bluetooth input when the default input is Bluetooth, to avoid profile switches that media apps read as route changes: [PR 1146](https://github.com/cjpais/Handy/pull/1146).
- Other effects: AirPods handoff stolen by a start sound played on the Mac ([Handy #646](https://github.com/cjpais/Handy/issues/646)), no audio captured while an iPhone plays through the same AirPods ([Handy #1990](https://github.com/cjpais/Handy/issues/1990)), the stem press shows "Cannot Control Mic with AirPods" ([Handy #2045](https://github.com/cjpais/Handy/issues/2045)), and a stale AUHAL with AirPods plus Logic Pro ([VoiceInk #956](https://github.com/Beingpax/VoiceInk/issues/956)). Clamshell mode disables the built-in mic ([VoiceInk #566](https://github.com/Beingpax/VoiceInk/issues/566)).
- Design (judgment): setting "Input device: Auto". Pick the built-in mic when the default input is Bluetooth and the lid is open. In clamshell mode pick the next non-Bluetooth input. Let the user override. Do not play sounds through the Bluetooth route.

Notes:

- FluidAudio coverage (README and release notes): Parakeet v2, v3, Ultra, Redux, Phonon-2, TDT-CTC-110M, Parakeet EOU (English, 120M), Nemotron streaming, Cohere Transcribe beta, SenseVoice, Paraformer, Silero VAD, diarization, TTS. Package traits can be turned off with `traits: []` to build ASR and VAD only. Apache 2.0. Needs Swift 6.2 and Xcode 26. Sources: [README](https://github.com/FluidInference/FluidAudio), [v0.17.5](https://github.com/FluidInference/FluidAudio/releases/tag/v0.17.5).
- The Nemotron multilingual streaming build (about 40 languages including German) is local-path-only in FluidAudio, with no published Core ML repo. You would have to convert it on Linux with CUDA: [NemotronMultilingual.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/NemotronMultilingual.md). Not shippable in v1.
- WhisperKit open-source covers tiny, base, small and two large-v3 turbo builds, plus Core ML distil variants on the hub. Requires macOS 14+. MIT. Argmax keeps real-time transcription with speakers and custom vocabulary in a Pro SDK. Sources: [README](https://github.com/argmaxinc/WhisperKit), [HF hub listing](https://huggingface.co/argmaxinc/whisperkit-coreml/tree/main). The Argmax paper reports 0.46 s latency and 2.2 percent WER against server systems ([arXiv 2507.10860](https://arxiv.org/abs/2507.10860)), hardware not stated.
- whisper.cpp: Metal runs on the GPU, a Core ML encoder on the ANE is "more than x3 faster" than CPU-only, Silero VAD via `--vad`, MIT, precompiled XCFramework. It adds a fourth runtime without covering a model that WhisperKit does not. Source: [README](https://github.com/ggml-org/whisper.cpp).
- mlx-audio covers Whisper, Distil-Whisper, Qwen3-ASR, Parakeet, Nemotron 3.5 streaming (40 locales), Voxtral and Voxtral Realtime, with a Swift package ([mlx-audio](https://github.com/Blaizzy/mlx-audio), [mlx-audio-swift](https://github.com/Blaizzy/mlx-audio-swift)). Use it only if you add MLX for the LLM anyway, and want Qwen3-ASR or Voxtral.
- Reliability caveats from users: Parakeet models failed silently on M5 and macOS 27.0 with "Failed to prepare the model for predictions" ([VoiceInk #987](https://github.com/Beingpax/VoiceInk/issues/987)). A SIGSEGV in `MLE5ProgramLibrary` on macOS 27.0.1 ([VoiceInk #1007](https://github.com/Beingpax/VoiceInk/issues/1007)). First dictation after idle took 45 to 55 s because the Neural Engine compile cache was not warm ([VoiceInk #1003](https://github.com/Beingpax/VoiceInk/issues/1003)). ## 5. Local LLM cleanup

Apple Foundation Models:

- `SystemLanguageModel`: on-device, macOS 26+, three model versions (OS 26.0 to 26.3, 26.4, 27.0), availability states `.available`, `.unavailable(.deviceNotEligible)`, `.unavailable(.modelNotReady)`. `supportsLocale(_:)` and `supportedLanguages` exist. Source: [Apple docs](https://sosumi.ai/documentation/foundationmodels/systemlanguagemodel).
- Context window: 4096 tokens per session, shared by instructions, prompts, tool schemas, `Generable` schemas and responses. Exceeding it throws `exceededContextWindowSize`. A token is about 3 to 4 characters in Latin languages. `contextSize` and `tokenCount(for:)` arrived in 26.4. Source: [TN3193](https://developer.apple.com/tutorials/data/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window.md). A 100-word German dictation is a few hundred tokens each way, which fits.
- Size: about 3B parameters with 2-bit quantization-aware training ([Apple tech report](https://machinelearning.apple.com/research/apple-foundation-models-tech-report-2025)). The report names no German.
- Guided generation: `@Generable` and `@Guide` return typed output. Tight schemas cost tokens ([TN3193](https://developer.apple.com/tutorials/data/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window.md)). For cleanup, plain string output with a one-paragraph instruction is cheaper.
- WWDC26: rebuilt on-device model, new token-count APIs, framework becoming open source, a model abstraction layer ([session 241](https://developer.apple.com/videos/play/wwdc2026/241), [MacRumors](https://www.macrumors.com/2026/06/09/apple-outlines-major-ai-and-developer-tool-updates/)). Whether German is supported by the on-device model: unverified. Check `supportsLocale` for `de`.
- Availability limits: needs Apple Intelligence-eligible hardware and region. Handle `.unavailable` and fall back to rules only.

MLX Swift LM:

- [ml-explore/mlx-swift-lm](https://github.com/ml-explore/mlx-swift-lm): MIT, release 3.32.3 (2026-09-30), LLM and VLM, LoRA, `MLXGuidedGeneration` (JSON schema or EBNF), and `MLXFoundationModels`, a bridge that lets an MLX model run behind `LanguageModelSession` (needs the macOS 27 SDK). The README example uses `LLMRegistry.qwen3_0_6b_4bit`. VoiceInk already depends on `mlx-swift-lm`.
- llama.cpp: not evaluated in depth. Superwhisper's S1-mini ships as GGUF. Using it means a fourth native dependency. Judgment: skip unless a GGUF-only model is required.

Latency budget for about 100 words (judgment, not measured):

- Output is roughly 130 to 200 tokens (English and German differ). At 45 tokens/s that is 3 to 4.5 s for a 3B model, which is too slow for a "very fast" product.
- Spokenly reports about 0.2 s for 1 to 2 sentences and 5 to 15 s for several hundred words on Mac, with a dedicated small model ([docs](https://spokenly.app/docs/macos/local-model-cleanup)).
- Wispr Flow reports under 700 ms P99 end to end on server GPUs with fine-tuned Llama (vendor case study): [Baseten](https://baseten.co/customers/wispr-flow).
- Plan: a deterministic pass first (filler list, spacing, casing, replacements), then the LLM only when the text has more than N words or when the user asks. Set a hard timeout (for example 1.5 s) and insert the rules-pass result on timeout. Measure Apple Foundation Models and Qwen3 0.6B and 1.7B on your own German and English samples before you fix N.
- Guard against over-editing. Spokenly leaves text alone above about 1,600 words and does not follow dictated instructions or answer questions. A length-ratio check (fall back to raw if the output keeps under half the words of a 40+ word input) is described in a search summary of Spokenly and is unverified.

How others prompt cleanup:

- VoiceInk: XML-tagged prompt with `<TASK>`, `<RULES>`, `<EXAMPLES>`, and the transcript wrapped in `<TRANSCRIPT>`. The default task is "Clean <TRANSCRIPT> into polished, readable, general-purpose text", with the rule to preserve dictated greetings and not add any that were not spoken, and one worked example that formats a spoken list. There is also a user-editable filler word list. Sources: [PromptTemplates.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Enhancement/Templates/PromptTemplates.swift), [AIEnhancementService.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Enhancement/Workflows/AIEnhancementService.swift), [FillerWordManager.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Enhancement/State/FillerWordManager.swift).
- Superwhisper S1-mini: no free prompt. Input is `[Styling: semi-formal] [Structure: prose] [Context: general]` plus the raw transcript. The card warns that changing wording or values causes garbled output. Segment-by-segment, so self-corrections across segments are missed. Source: [BetterStack](https://betterstack.com/community/guides/ai/s1-mini.md).
- Wispr Flow: fine-tuned Llama for real-time cleanup, using user context and preferences ([Baseten case study](https://baseten.co/customers/wispr-flow)). Prompt text is not public (unverified). One analysis says it sends accessibility text, app context and proper nouns with the audio: [wensenwu.com](https://wensenwu.com/thoughts/wispr-flow-investigation).

## 6. Text insertion

Methods:

| Method                            | Pros                                        | Cons                                                                                                                                                                        |
| --------------------------------- | ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pasteboard plus synthesized Cmd+V | Works in most apps, handles long text, fast | Clobbers the clipboard, races with restore, fails in some Chromium fields, needs Accessibility                                                                              |
| AX `kAXSelectedTextAttribute` set | No clipboard use                            | Not supported by all apps and web fields (unverified). VoiceInk's users fall back to Edit > Paste through AX ([#1000](https://github.com/Beingpax/VoiceInk/issues/1000))    |
| `CGEvent` unicode typing          | No clipboard use                            | Slow for long text, collides with held modifiers ([FluidVoice #940](https://github.com/altic-dev/FluidVoice/issues/940)), per-event length limit from memory and unverified |

VoiceInk reference implementation ([CursorPaster.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/CursorPaster.swift), [ClipboardManager.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Infrastructure/SystemIntegration/Paste/ClipboardManager.swift)):

- Serializes paste sessions in a queue.
- Snapshots all items and types if restore is enabled.
- Writes the string plus `org.nspasteboard.source`, and when restoring also `org.nspasteboard.TransientType` and `org.nspasteboard.AutoGeneratedType`, plus a private session type used to check ownership later.
- Waits 0.20 s before posting the paste.
- Posts Cmd down, V down, V up, Cmd up with a private event source, virtual key 0x37 and 0x09, 10 ms apart, flags set on the key events.
- Checks `AXIsProcessTrusted()` first.
- Restores only after at least 0.25 s and only if the pasteboard still holds its own session marker.
- Has an AppleScript path with `key code 9` when the input source switches to QWERTY on Command (keyboard layout names ending with the Command symbol).

Known failures:

- Restore before the target app reads the pasteboard pastes the old content: [VoiceInk #415](https://github.com/Beingpax/VoiceInk/issues/415), [OpenWhispr #1740](https://github.com/OpenWhispr/openwhispr/issues/1740), [Handy #502](https://github.com/cjpais/Handy/issues/502). VoiceInk's fix keeps the transcript in the clipboard by default and makes restore opt-in with a delay.
- Chromium web fields drop the synthetic paste on repeat dictations. `killall pboard` helps temporarily: [VoiceInk #1000](https://github.com/Beingpax/VoiceInk/issues/1000).
- Paste goes to a stale window in Screen Sharing: [VoiceInk #928](https://github.com/Beingpax/VoiceInk/issues/928). Two system click sounds on insert: [VoiceInk #933](https://github.com/Beingpax/VoiceInk/issues/933).
- Skipping Accessibility during onboarding turns auto-paste into silent copy-only: [OpenWhispr #2606](https://github.com/OpenWhispr/openwhispr/issues/2606). Clipboard managers record the dictated text unless transient types are set (Handy asks for the Wayland equivalent in [#2072](https://github.com/cjpais/Handy/issues/2072)).
- The `org.nspasteboard.*` markers come from the nspasteboard.org convention. I did not fetch the spec page. VoiceInk's use of the three types is the primary evidence.

Design (judgment): default is paste with transient types, always set. Restore the previous clipboard only if enabled and the marker still matches. Show a clear message when Accessibility is missing. Add an AX or menu-based paste fallback and retry once if the target text did not change (read back through AX where possible).

## 7. Personalization

Whisper prompt biasing:

- The prompt is capped at 224 tokens, only the last 224 are used, and the rest is dropped without a warning. Whisper imitates style and spelling from the prompt. It does not follow instructions. A prompt cannot override audio. Results are unreliable. Source: [OpenAI cookbook](https://developers.openai.com/cookbook/examples/whisper_prompting_guide).
- WhisperKit exposes `promptTokens` and `prefixTokens` in `DecodingOptions`. Prompt tokens are trimmed to half of the 448 token context minus one, so 223 tokens. An empty prompt is skipped because a bare start-of-previous token ends segments early. Source: [TextDecoder.swift](https://github.com/argmaxinc/WhisperKit/blob/main/Sources/WhisperKit/Core/TextDecoder.swift). The WhisperKit README lists "custom vocabulary" under the Pro SDK, so the open-source path is prompt tokens only.
- Multilingual damage: with dictionary entries passed as context, English speech was sometimes transcribed in Polish even with English forced. Removing the entries fixed it: [OpenWhispr #2628](https://github.com/OpenWhispr/openwhispr/issues/2628). Scope vocabulary per language.

Parakeet and FluidAudio:

- FluidAudio documents CTC vocabulary boosting (NVIDIA NeMo CTC word spotter, [arXiv 2406.07096](https://arxiv.org/abs/2406.07096)). For Parakeet TDT 0.6B v2 and v3 it uses a separate CTC encoder, about 130 MB and 26x real time, versus a built-in CTC head for the 110M hybrid model. It rescoring replaces words after the TDT decode. The doc claims 99.4 percent accuracy for both approaches on its test (the test set is not described in the portion I read). Source: [CustomVocabulary.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/CustomVocabulary.md). The README itself says it documents no dedicated API, so rely on the doc, and test with German terms (unverified for German).
- Parakeet Ultra and Redux share the v3 decode path (`isV3Family`), so the same boosting should apply (unverified).

SpeechAnalyzer:

- `AnalysisContext` carries `contextualStrings` (words and phrases grouped by `ContextualStringsTag`) and `userData`. `SpeechAnalyzer.setContext(_:)` replaces the current context, not a merge. Sources: [AnalysisContext](https://sosumi.ai/documentation/speech/analysiscontext), [setContext](<https://sosumi.ai/documentation/speech/speechanalyzer/setcontext(_:)>). Effect size and German support: unverified. `SFCustomLanguageModelData` is listed as related for custom vocabulary.

LLM-side:

- Put the user's vocabulary in the cleanup prompt and apply a deterministic replacement list before and after the LLM. Keep entries short. Mind the 4096-token budget for Apple's model.

Learning from corrections:

- VoiceInk Auto-Learn: after paste, it observes the focused field through AX (`AXUIElement`, focused element, text value), tracks the pasted range, diffs the final text, queues candidates, and asks an LLM reviewer to propose "replacement and vocabulary", "replacement only" or "vocabulary only". Modes are manual review or immediate. Sources: [AutoLearn directory](https://github.com/Beingpax/VoiceInk/tree/main/VoiceInk/Features/Dictionary/AutoLearn), [AutoLearnTypes.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Dictionary/AutoLearn/AutoLearnTypes.swift).
- Failure modes: review queue shows "1 correction" then "No corrections to review", and immediate mode learns nothing ([VoiceInk #985](https://github.com/Beingpax/VoiceInk/issues/985)). A second paste replaces the first monitor and an old callback applies the wrong original text ([OpenWhispr #2611](https://github.com/OpenWhispr/openwhispr/issues/2611)). Web fields need text normalization (VoiceInk normalizes line endings and invisible characters).
- Wispr Flow also compares dictated text with later edits, according to one analysis ([wensenwu.com](https://wensenwu.com/thoughts/wispr-flow-investigation)). This is the data that raised the privacy concern, so keep it local and visible.
- Design (judgment): one active observation session at a time, bound to a paste token. Finalize when focus leaves the field or after a deadline. Show proposals for review first, then add an auto mode. Use a word-level diff with a minimum similarity gate before proposing a rule.

Storage:

- SwiftData in VoiceInk for dictionary, replacements and review proposals ([AutoLearnService.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Dictionary/AutoLearn/AutoLearnService.swift) takes a `ModelContainer`). I found no source comparing SwiftData and GRDB for this workload (unverified). Wispr stored a 694 MB local SQLite history including audio in one user's analysis ([wensenwu.com](https://wensenwu.com/thoughts/wispr-flow-investigation)). Do not store audio by default. A competitor review criticizes Superwhisper for saving audio by default ([Spokenly blog](https://spokenly.app/blog/superwhisper-review), competitor source).

## 9. Notch recording indicator

Goal: a quiet, polished animation around the MacBook notch while recording.

Decision: voz builds this UI from scratch. It does not depend on DynamicNotchKit, boring.notch or any other notch library, and it does not reuse code from the owner's NotchChat project. Those projects are reference only. Copy the technique (window level, collection behavior, shape path, spring values). Avoid their failure modes (oversized click-blocking panels, always-on hover tracking, drawing on non-notch screens). Note boring.notch is GPL-3.0 (license from memory, unverified here), so do not copy its code.

### 9a. Window recipe

Notch geometry, from DynamicNotchKit ([NSScreen+Extensions.swift](https://github.com/MrKai77/DynamicNotchKit/blob/main/Sources/DynamicNotchKit/Utility/NSScreen%2BExtensions.swift)):

- `hasNotch` is true when `auxiliaryTopLeftArea?.width` and `auxiliaryTopRightArea?.width` are both non-nil.
- Notch width is `frame.width - leftArea.width - rightArea.width`. Notch height is `safeAreaInsets.top`. Notch frame is centered on `frame.midX` at `frame.maxY - height`.
- Fallback without a notch: DynamicNotchKit uses the menu bar height (`frame.maxY - visibleFrame.maxY`) and a fixed 300 pt width. VoiceInk uses `NSStatusBar.system.thickness` and 180 pt.
- Apple's page for `auxiliaryTopLeftArea` was not available through the mirror (404). `safeAreaInsets` is described as "the distances from the screen's edges at which content isn't obscured" ([Apple](https://sosumi.ai/documentation/appkit/nsscreen/safeareainsets)). The meaning of `auxiliaryTop*Area` comes from the apps' usage, not from Apple text (unverified).
- boring.notch checks `screen.safeAreaInsets.top > 0` to decide if a screen has a notch ([matters.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/sizing/matters.swift)).

Recipe for voz (judgment, based on those four):

- `NSPanel`, `.borderless` plus `.nonactivatingPanel`, `isOpaque = false`, clear background, no shadow, `isFloatingPanel = true`, `canBecomeKey` and `canBecomeMain` false, `ignoresMouseEvents = true`.
- Level `.statusBar + 3` or `.mainMenu + 3`. Both appear above the menu bar in the apps above. The menu bar's own level is not in the sources I read (unverified).
- `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary, .stationary, .ignoresCycle]` to show on all Spaces and over full-screen apps.
- `orderFrontRegardless()` so it appears without activating voz.
- Size the panel to the widest the shape reaches, not half the screen. DynamicNotchKit's oversize panel blocks clicks once `ignoresMouseEvents` is false ([#48](https://github.com/mrkai77/DynamicNotchKit/issues/48)). With `ignoresMouseEvents = true` this does not happen, but a small panel is still cheaper to composite.
- Set the frame before ordering the window front. DynamicNotchKit reports the animation sometimes flies in from the left on MacBook Air M2 ([#30](https://github.com/mrkai77/DynamicNotchKit/issues/30), cause not stated in the issue).

Screens:

- Pick the screen by the active context. `NSScreen.main` can be nil in an agent app. VoiceInk falls back to the screen under the mouse, then the first screen ([RecorderScreenResolver.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Recording/Presentation/RecorderScreenResolver.swift)). A better pick for voz (judgment) is the screen of the focused window, since the user looks there.
- No notch (external display, older Mac, clamshell): do not draw a notch. boring.notch draws a black shape on screens without a physical notch and users report a 1 px line, hidden menu items and notch overlays in clamshell mode ([#892](https://github.com/TheBoredTeam/boring.notch/issues/892), [#940](https://github.com/TheBoredTeam/boring.notch/issues/940), [#1281](https://github.com/TheBoredTeam/boring.notch/issues/1281)). For voz, show a small pill centered under the menu bar on those screens, or nothing.
- Multiple screens: DynamicNotchKit shows on one screen per instance; showing on all screens through a loop showed only the last ([#18](https://github.com/mrkai77/DynamicNotchKit/issues/18)). Create one panel per target screen yourself. voz needs only the one screen.
- Rebuild or reposition on `NSApplication.didChangeScreenParametersNotification` and on wake. Reports of a missing panel after sleep: [VoiceInk #898](https://github.com/Beingpax/VoiceInk/issues/898), [boring.notch #336](https://github.com/TheBoredTeam/boring.notch/issues/336), [#420](https://github.com/TheBoredTeam/boring.notch/issues/420). The notification names are from my knowledge of AppKit, not from these sources.

### 9c. Live level meter

VoiceInk's metering path is a reference:

- It reads `averagePower` and `peakPower` (dB) from an `AVAudioRecorder`-style meter, maps -60 dB to 0 dB linearly to 0 to 1, and applies an exponential moving average of 0.6 old plus 0.4 new on each read ([Recorder.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Recording/Capture/Recorder.swift)).
- The view samples that value from a `TimelineView` at 16 ms minimum interval and shapes each bar with `pow(level, 0.7)`, a phase-shifted sine, and a center boost.

For voz with `AVAudioEngine` (judgment):

- In the tap block, compute RMS over the buffer (Accelerate `vDSP_rmsqv`), convert to dB, map -60 to 0 dB to 0 to 1.
- Store the result in one atomic or lock-protected `Float`. Do not publish a SwiftUI state change from the tap. The tap runs off the main thread ([Apple](<https://sosumi.ai/documentation/avfaudio/avaudionode/installtap(onbus:buffersize:format:block:)>)).
- Smooth in the view, on the display clock: fast attack (about 0.4 to 0.6 weight) and slower release (about 0.1 to 0.2 weight). These are starting values.
- Render with `TimelineView(.animation)` and `Canvas` so SwiftUI redraws once per display frame without view diffing for each bar. The `paused:` and `minimumInterval:` parameters exist on `.animation` ([Apple summary](https://sosumi.ai/documentation/swiftui/timelineview) was generic and I could not confirm the text, so treat as unverified). Pause the timeline when the panel is hidden.
- 120 Hz: `.animation` follows the display refresh rate by design (unverified in the Apple text I could read). VoiceInk caps at about 60 Hz with a 16 ms interval. A Core Animation alternative (`CAShapeLayer` bars with `CABasicAnimation`) avoids SwiftUI diffing. I found no benchmark comparing the two (unverified). Profile with Instruments (Time Profiler, Core Animation) on a ProMotion MacBook, and set a CPU budget.
- Idle cost lessons from Handy: stop overlay animation while hidden ([#1445 referenced in #1872](https://github.com/cjpais/Handy/issues/1872)), throttle mic-level updates, and do no level work while idle. A WebKit leak came from overlay mic-level events ([#1447](https://github.com/cjpais/Handy/issues/1872)).

### 9d. Shape and springs

Shape (from [DynamicNotchKit NotchShape.swift](https://github.com/MrKai77/DynamicNotchKit/blob/main/Sources/DynamicNotchKit/Views/NotchShape.swift) and [boring.notch NotchShape.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/components/Notch/NotchShape.swift)):

- A SwiftUI `Shape` with two animatable values, `topCornerRadius` and `bottomCornerRadius`, exposed through `animatableData` as an `AnimatablePair`.
- Path: start at the top-left, a quad curve down into the left edge (control point at the top of the inner x), a line down, a quad curve into the bottom edge, a line across, and the mirror on the right. The top corners curve inward so the shape flows out of the screen edge like the physical notch.
- boring.notch defaults: top radius 6, bottom radius 14 (init defaults). It switches between closed and open radius pairs by state.
- For a close match to the hardware notch, set the closed shape width and height to the measured notch size, and fill black. The indicator then looks like the notch grows wings.

Spring values in use:

| Source                         | Open                                                                  | Close                                                                                                                                                                                                                                     |
| ------------------------------ | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DynamicNotchKit style defaults | `.bouncy(duration: 0.4)` (notch), `.snappy(duration: 0.4)` (floating) | `.smooth(duration: 0.4)`, conversion `.snappy(duration: 0.4)` ([DynamicNotchStyle.swift](https://github.com/MrKai77/DynamicNotchKit/blob/main/Sources/DynamicNotchKit/DynamicNotch/DynamicNotchStyle.swift))                              |
| boring.notch                   | `spring(response: 0.42, dampingFraction: 0.8)`                        | `spring(response: 0.45, dampingFraction: 1.0)`. Interactive variant `interactiveSpring(response: 0.38, dampingFraction: 0.8)` ([ContentView.swift](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/ContentView.swift)) |
| VoiceInk notch recorder        | `spring(response: 0.42, dampingFraction: 0.80)`                       | `spring(response: 0.45, dampingFraction: 1.0)` ([NotchRecorderView.swift](https://github.com/Beingpax/VoiceInk/blob/main/VoiceInk/Features/Recording/Views/NotchRecorderView.swift))                                                      |

Starting point for voz (judgment): open with `spring(response: 0.42, dampingFraction: 0.8)` for a small overshoot, close with `spring(response: 0.45, dampingFraction: 1.0)` for no bounce. Animate width and the two corner radii together. Cancel and retarget from the current value when the key is released mid-open (SwiftUI springs are interruptible). Fade the bars in after the width passes about 60 percent. Honor Reduce Motion by cross-fading instead of widening (judgment).

### 9e. Notch app issues to design around

No model found beats Parakeet TDT v3 for voz when latency, footprint and a Swift path are weighed together. Parakeet v3 stays the default. Whisper large-v3-turbo stays the second model. Reasons are below.

### 10.3 Newer releases checked

### 10.4 Code-switching, hallucination, mixed speech

- Code-switching DE and EN: no primary source reports it for Parakeet v3, Canary, Whisper turbo, Voxtral or Qwen3-ASR. The Parakeet v3 card does not mention it ([card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)). The Qwen3-ASR card does not mention it. Unverified for all. This is the main reason to ship a second model and a per-language setting.
- Language handling: Parakeet v3 detects the language itself, no prompt needed (card). Cohere needs the language passed explicitly ([doc](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md)).
- Hallucination: the Whisper turbo card says output "may include texts that are not actually spoken" and is "prone to generating repetitive texts" ([card](https://huggingface.co/openai/whisper-large-v3-turbo)). WhisperKit open issues in the last 6 months include empty transcripts from sampler bugs ([#539](https://github.com/argmaxinc/argmax-oss-swift/issues/539)) and wrong word timestamps with prompt tokens ([#542](https://github.com/argmaxinc/argmax-oss-swift/issues/542)). I found no Parakeet hallucination statement on the card (unverified). FluidAudio issue [#954](https://github.com/FluidInference/FluidAudio/issues/954) reports duplicated words on long audio in v0.17.0, and [#912](https://github.com/FluidInference/FluidAudio/issues/912) and [#899](https://github.com/FluidInference/FluidAudio/issues/899) report wrong text at chunk boundaries or from vocabulary boosting. Dictation clips are short, so the long-audio ones matter less. Custom vocabulary on v3 is [#967](https://github.com/FluidInference/FluidAudio/issues/967): good recall, but common words get replaced. Test before you turn it on.
- Cohere: [#1013](https://github.com/FluidInference/FluidAudio/issues/1013) says the 108-slot decoder cache dropped a third of words on dense speech. Fixed by the 256-slot v3 decoder, per the doc.

### 10.5 Speed on Apple Silicon

- Parakeet v3 on M4 Pro: RTFx 220.9 on German FLEURS, 207.4 on English FLEURS (FluidAudio benchmarks, link above). A 10 s clip is then about 0.05 s of compute, excluding model load and audio capture. This is arithmetic on a corpus average, not a measured 10 s clip.
- Third-party speed test on an M4 with 24 GB, one short sentence, clip length not stated, date not stated: FluidAudio Parakeet v2 0.19 s, mlx-whisper large-v3-turbo 1.02 s, whisper.cpp large-v3-turbo-q5_0 1.23 s, WhisperKit large-v3 (not turbo) 2.22 s ([mac-whisper-speedtest](https://github.com/anvanvan/mac-whisper-speedtest)). The WhisperKit row ran a larger model, so it is not a runtime comparison.
- Whisper large-v3-turbo on Apple Silicon: no first-party 10 s number found for WhisperKit or whisper.cpp (unverified).
- Cohere on M4 Pro: RTFx 1.98 on German. About 3 minutes first-load compile on M2. Not suited to push-to-talk ([doc](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Cohere.md)).
- Compile cost: FluidAudio documents Core ML first-load compile for the v3 encoder at 3.4 s on iPhone 16 Pro Max cold, 0.16 s warm (benchmarks link above). No Mac cold-start figure for v3 found. VoiceInk reported 45 to 55 s after idle on one setup ([VoiceInk #1003](https://github.com/Beingpax/VoiceInk/issues/1003)). Load the model at launch and run one dummy inference.

### 10.6 Q2: FluidVoice and FluidAudio

FluidVoice is not a runtime. It is a GPL-3.0 macOS dictation app by altic-dev ([repo](https://github.com/altic-dev/FluidVoice)). Its `Package.swift` depends on a fork of FluidAudio (`altic-dev/FluidAudio`), on `transcribe-cpp-swift`, and on a fork of DynamicNotchKit ([Package.swift](https://github.com/altic-dev/FluidVoice/blob/main/Package.swift)). If you meant a runtime, you meant FluidAudio from FluidInference. FluidVoice is a competitor and a reference. Do not copy code from it, because GPL-3.0 would bind voz.

### 10.8 Recommendation

- Default model: Parakeet TDT 0.6B v3 via FluidAudio. German is within about half a point of the best Open ASR entry (4.90 vs 4.50). It is about 480 MB, runs far faster than real time, and detects the language by itself.
- Second model: Whisper large-v3-turbo via WhisperKit. It covers a different failure profile for mixed speech and gives a fallback if Parakeet fails on macOS 27. Evaluate the primeline German fine-tune only if your recordings show German errors, and only after you confirm a Core ML or GGML conversion path (unverified).
- Test before adopting: Parakeet Ultra (same runtime, one enum change), and Apple SpeechAnalyzer as a zero-download option. Check `SpeechTranscriber.supportedLocales` for German on your target OS.
- Runtimes: FluidAudio plus WhisperKit. Keep whisper.cpp as the reserve if the Core ML or ANE path breaks on macOS 27 for both.
- Drop from the shipping list in section 4: Cohere Transcribe (RTFx 1.98, 3 minute compile, beta), Whisper small (large-v3-turbo replaces it), Distil-Whisper large-v3 (English only, Parakeet and Phonon-2 cover English), Parakeet Redux (minute-long ANE compile) and Phonon-2 (English only, no gain over v3 and Ultra for a bilingual user), Nemotron EN streaming (English only, push-to-talk does not need streaming). Do not pursue Voxtral Realtime, Granite 5.0, Kyutai, Canary-Qwen or Phi-4 for v1: no usable Swift path or too large.
- New shipping list: Apple SpeechAnalyzer (optional, after German check), Parakeet v3 (default), Parakeet Ultra (optional), Whisper large-v3-turbo (second).
- Required checks before launch: German plus mixed DE and EN recordings from the user, word error rate for v3, Ultra, turbo and SpeechAnalyzer, cold start after idle on macOS 26 and 27, and behavior of the menu-bar app when backgrounded.
