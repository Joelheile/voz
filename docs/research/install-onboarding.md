# Install, onboarding, update and extensions for non-technical users, no paid Developer ID

Research date: 2026-10-17. Scope: the full path from "download voz" to "first dictation" to "first extension install" for a non-technical macOS user, assuming voz stays unsigned or ad-hoc signed (no $99/year Apple Developer Program membership, no Developer ID, no notarization).

This file builds on, and does not repeat, `docs/research/distribution.md` (Gatekeeper mechanics, Homebrew policy, curl install script, Developer ID cost and free-tier options) and `docs/research/update-and-test.md` (Sparkle, CI signing, TCC/designated-requirement mechanics, release pipeline). `docs/research/extension-security.md` already covers extension sandboxing and supply-chain policy. Read those first; this file picks up where they leave gaps: TCC identity specifics, real competing apps' onboarding, Bun/npm distribution without a terminal, and a concrete end-to-end flow with click counts.

Unverified claims are marked **[unverified]**, with the reason.

## 1. TCC identity: why grants reset, and what a stable identity requires

### cdhash versus designated requirement

TCC decides whether an updated binary is "the same app" the user already granted Microphone, Accessibility, or Input Monitoring access to by checking the binary's code-signing designated requirement (DR), not by bundle ID alone. `codesign -d -r-` prints the DR for any binary.

- A Developer ID signature's DR pins the certificate's team ID plus the bundle identifier, so every build signed by the same team ID is "the same app" to TCC, and grants survive rebuilds and updates.
- An ad-hoc signature (`codesign --sign -`) has no team ID. Its DR has nothing stable to pin to, so it falls back to pinning the specific binary's cdhash, a hash of the compiled binary itself. Every rebuild produces a different binary and a different cdhash, so every rebuild looks like a new, never-granted app to TCC.

This is corroborated by a secondary source mirrored across several documentation sites (a macOS permissions guide duplicated identically across roughly ten unrelated npm packages' docs, suggesting it is itself copied from one original, unidentified source): "Ad-hoc signatures generate a new identity every build... macOS will forget previous grants, and prompts can disappear entirely until the stale entries are cleared" **[secondary source, mirrored across multiple unrelated hosts, origin not identified; treat the general mechanism as credible, the exact wording as unverified against Apple's own documentation]**. voz's own `docs/releasing.md` and `docs/research/update-and-test.md` already describe the practical symptom correctly (grants reset on every signing-identity change); this section adds the cdhash-versus-team-ID mechanism underneath it, which neither file states explicitly.

Workaround suggested by that same secondary source: set an explicit identifier-based requirement at ad-hoc signing time with `codesign --sign - --requirements '=designated => identifier "com.joelheile.voz"'`. **[unverified, no primary Apple source found confirming TCC honors a custom requirement string on an ad-hoc signature the same way it honors a real certificate's DR; test on a throwaway build before relying on it]**.

### Recovery and testing

Apple's own `tccutil(1)` man page (confirmed directly on a local Mac via `man tccutil`, cited already in `update-and-test.md`) documents `tccutil reset <service> [bundle_id]` to clear stale grants for manual testing. There is no documented API to force a non-granted app back onto the Accessibility or Input Monitoring list; reset and re-grant is the only path.

### Free Apple ID "Personal Team" certificate

Xcode auto-creates a "Personal Team" for any Apple ID that is not enrolled in the paid Developer Program, letting Xcode manage a free Apple Development certificate for running your own code on your own devices.

- Lifetime: multiple Apple Developer Forum answers agree the resulting provisioning profile/certificate expires roughly **7 days** after creation, versus **1 year** for a paid-program certificate ([Apple Developer Forums thread 712540](https://developer.apple.com/forums/thread/712540); [MASTG-TECH-0079](https://mas.owasp.org/MASTG/techniques/ios/MASTG-TECH-0079/)). Apple has not published this limit as formal documentation; one Apple engineer on the forums states outright that Apple does not have formal documentation of the free-tier limits **[Apple engineer forum statement, not a published spec page; treat the 7-day figure as credible but not formally documented by Apple]**.
- Scope: a free Personal Team certificate is explicitly for running your own build on your own device via Xcode. It cannot generate a Developer ID Application certificate, cannot be used for notarization, and cannot be distributed to other users' Macs the way a paid-program cert can. It does not solve voz's distribution problem; it only helps the maintainer's own dev-loop signing, which is not the open question here (voz's dev loop already uses a self-signed local identity per `docs/releasing.md`).
- Because the cert expires weekly and is scoped to the enrolling Apple ID's own machine, it cannot serve as a stable signing identity for a public release artifact. It's a dead end for this question, not a cheaper substitute for Developer ID.

### Self-signed certificate with a stable local identity

voz already does the closest available free substitute: `docs/releasing.md` and `scripts/make-app.sh` describe a self-signed "voz Dev" identity imported into a keychain, used consistently across both local builds and CI, so every release is signed by the _same_ self-signed certificate rather than a fresh ad-hoc signature per build. This likely gives TCC a stable, non-ad-hoc code identity to key off (a self-signed cert with no team ID still has _some_ leaf certificate identity the DR can reference, unlike a bare `--sign -` ad-hoc signature, which has none).

**[unverified, no primary or credible secondary source found describing whether TCC's DR-matching treats a self-signed leaf certificate as equivalently stable to a CA-issued Developer ID leaf, or whether it still falls back to cdhash-based matching for any non-Apple-issued certificate]**. This is the single highest-value open question in this research: if a self-signed identity gives TCC a stable, non-cdhash DR, voz may already avoid the "reset every rebuild" problem for all builds using the same self-signed cert, independent of Developer ID. `docs/releasing.md`'s own statement, "macOS keeps microphone and Accessibility permissions across updates only when the signing identity stays the same," is consistent with this but does not independently confirm the DR mechanism; it may just be describing the observed behavior. Resolving this needs an empirical test: sign two different builds with the same self-signed "voz Dev" identity, check `codesign -d -r-` on both, and confirm TCC does not re-prompt between them on a real Mac.

### CGPreflight/CGRequest and AX APIs

Accessibility and Input Monitoring are two separate TCC services with separate APIs and separate prompting behavior, confirmed across multiple Apple Developer Forums threads:

- Accessibility: `AXIsProcessTrustedWithOptions` with the prompt option triggers the system Accessibility prompt and, per forum reports, adds the app to the Accessibility list automatically on first call.
- Input Monitoring: `CGPreflightListenEventAccess()` checks current status without prompting; `CGRequestListenEventAccess()` triggers the system prompt. A developer on Apple's own forums (thread 828052) reports a real, apparently still-open problem: `CGRequestListenEventAccess()` shows the system prompt once per install but does not reliably add the app to the Input Monitoring list in System Settings, with no confirmed answer from Apple staff on a reliable workaround **[primary source is a developer forum thread, not Apple's own API reference documentation; the underlying bug/limitation is credible but Apple has not confirmed a fix or workaround in the thread found]**.
- `AXIsProcessTrusted()` reflects only Accessibility status; it returns `false` even when Input Monitoring is granted. The two must be checked and requested independently, which matches what `Sources/Voz/Menu/SetupModel.swift` and `SetupPage.swift` already do (three separate `PermissionRow`s: Microphone, Accessibility, Input Monitoring, each with its own `fix` action).

### Deep links to System Settings panes

`x-apple.systempreferences:` URLs still open System Settings panes on current macOS, confirmed by a community-maintained reference list, but the exact bundle-identifier-style targets changed with the System Settings rewrite in macOS 13 and are not Apple-documented ([SystemSettings-URLs-macOS reference](https://github.com/jaywcjlove/SystemSettings-URLs-macOS)) **[community-maintained reference, not Apple documentation; confirm the exact pane identifiers voz uses against a real macOS 26 machine, since Apple does not publish or guarantee this URL scheme]**. voz's `SetupModel.swift` already uses `Permissions.openSettings(pane: "Privacy_Microphone")` and `"Privacy_ListenEvent"`, which are anchor fragments on the modern `com.apple.settings.PrivacySecurity.extension` pane rather than the old pre-Ventura `com.apple.preference.security` identifiers; this matches the current (post-macOS 13) scheme the reference above documents, and is consistent with what's already shipping, not a gap to fix.

### How real shipped apps handle this onboarding

- **Superwhisper**: docs describe a two-permission first-launch flow, Microphone then Accessibility, with guided onboarding into language/model choice and a first dictation, and a note that skipped permissions can be granted later in Settings ([superwhisper docs, quickstart](https://superwhisper.com/docs/get-started/quickstart.md)). This is structurally the same shape as voz's existing `SetupPage.swift`, just with one fewer permission (voz also needs Input Monitoring, for its hold-to-talk hotkey).
- **OpenWhispr**: its macOS docs state the same two permissions (Microphone, Accessibility) and explicitly document the unsigned-build Gatekeeper workaround as part of onboarding: "on first launch, macOS may show a security warning for unsigned builds. Right-click the app and select Open to bypass this" ([OpenWhispr macOS docs](https://docs.openwhispr.com/platform/macos.md)). This instruction is stale for current macOS: Sequoia removed the Control-click/right-click "Open" bypass (confirmed already in `distribution.md`), so this documented flow no longer works as written on macOS 15+ and would need the System Settings > Open Anyway flow instead. This is a concrete example of a real competing app's own docs being out of date against current Gatekeeper behavior, worth avoiding in voz's own onboarding copy.
- **VoiceInk, OpenSuperWhisper, Handy**: no primary source (README, docs site, or repo) was found describing their first-launch permission flow or confirming their Gatekeeper/signing status in this research pass. `update-and-test.md` already inspected VoiceInk's release script directly and confirmed it signs and notarizes locally before publishing, which implies VoiceInk ships Developer-ID-signed, sidestepping this whole problem, but that file did not check VoiceInk's onboarding UI, and this pass found no public source describing it either. **[open, flagged below]**
- **Ice vs IceMelt**: already covered in `distribution.md` section 5. IceMelt exists specifically because it pays for Developer ID signing where the original Ice project does not reliably; a real GitHub issue shows an Ice user needing to manually run `sudo xattr -dr com.apple.quarantine` post-install ([Ice issue #711](https://github.com/jordanbaird/Ice/issues/711)), consistent with "Homebrew cask" alone not removing Gatekeeper friction for an unsigned app, which `distribution.md` already states. Third-party aggregator sites (not primary) report conflicting signing status for Ice and Rectangle; this research could not resolve those conflicts from primary README/release text in this pass either, the same gap `distribution.md` already flagged as unverified.

## 2. Sparkle updates without Developer ID, and the TCC interaction

Sparkle's own setup documentation treats Developer ID signing as a recommendation, not a requirement: "Notarize and code sign the application via Apple's Developer ID program (if possible)" ([Sparkle, Basic Setup/documentation index](https://sparkle-project.org/documentation/)). Sparkle's only hard requirement around signing is narrower and is already correctly handled in voz's pipeline: ad-hoc signing with Library Validation enabled (part of the hardened runtime) can block loading `Sparkle.framework` unless the entitlement is disabled, which is exactly why `Resources/voz.entitlements` carries `com.apple.security.cs.disable-library-validation` today, as `docs/releasing.md` and `update-and-test.md` already document.

Sparkle updates install without a fresh quarantine-driven Gatekeeper dialog regardless of signing identity, because Sparkle's downloader uses `URLSession`, not a quarantine-aware app, the same reasoning `distribution.md` already gives for why `curl` downloads aren't quarantined. This means: for a voz user who got past the _first_ unsigned/ad-hoc-signed launch once (via System Settings > Open Anyway), every subsequent Sparkle-delivered update installs silently, with no repeat of the Gatekeeper dialog. This is a genuinely good property of the self-signed/unsigned path that is easy to undervalue: the Gatekeeper friction in this research is a **one-time cost per install**, not a recurring one, as long as the signing identity never changes.

The TCC interaction follows directly from section 1: Sparkle updates keep TCC grants intact exactly when, and only when, every release is signed with the same stable identity (whether that's a future Developer ID cert or, pending the open question in section 1, possibly voz's existing self-signed "voz Dev" identity). This is the same conclusion `docs/releasing.md` and `update-and-test.md` already state for the Developer ID migration case; this research's addition is that the self-signed case may already have this property today, unverified pending the open question above.

### Alternatives to Sparkle as the update path

- **`brew upgrade`**: this only works if voz ships via a Homebrew cask, which `distribution.md` section 2 already rules out for the official tap (Homebrew's Gatekeeper-compliance deadline, confirmed above as now active policy) and treats as not removing Gatekeeper friction even on a third-party tap, it just changes how the file lands on disk. No primary source found describing whether `brew upgrade` on an unsigned cask re-triggers a quarantine check differently than a fresh `brew install`; `distribution.md` already notes Homebrew deliberately re-applies quarantine on cask installs. **[unverified for the upgrade case specifically, treat as behaving the same as install, no evidence found to the contrary]**. Given the cask path is already closed off by Homebrew's own policy, this isn't a live option regardless.
- **Self-update via re-running `install.sh`**: scriptable, and would behave exactly like today's manual `scripts/install.sh` run, consistent (not quarantined, since curl-fetched; no dialog on every update). The real cost is UX, not technical: it requires the user (or voz itself, via a background shell call) to re-run a Terminal command on every update, which is a worse experience than Sparkle's fully-automatic, no-terminal background install, and reintroduces exactly the "pipe curl to sh" trust question `distribution.md` section 3 already covers for first install. Not recommended as a _replacement_ for Sparkle; Sparkle already works today and doesn't carry this cost.

## 3. Extensions with zero terminal use

### Downloading Bun without Gatekeeper friction

`docs/extensions.md` already states voz downloads Bun 1.4.3 into `~/Library/Application Support/voz/bun` and checks its SHA-256. This download happens via app code (presumably `URLSession`), not a browser, so by the same quarantine mechanism `distribution.md` documents (only quarantine-aware apps like browsers, Mail, or Messages set `com.apple.quarantine`), **a Bun binary downloaded by voz's own Swift code is not quarantined and triggers no Gatekeeper dialog**, the same reasoning that makes Sparkle's in-app updates silent. This is a genuine advantage of voz downloading Bun itself rather than asking the user to download and run a Bun installer manually.

Whether Bun's own macOS release binary is itself signed or notarized by Oven (the maintainer) could not be confirmed in this research pass. Bun's GitHub Releases page assets did not load their filenames in the fetch performed here, and no Bun documentation page mentioning code signing or notarization was found by search ([Bun releases](https://github.com/oven-sh/bun/releases/latest)). **[open, flagged below, needs a direct `codesign -dv` check on a downloaded `bun-darwin-aarch64` binary]**. This matters less for voz than it would for a browser-downloaded app: since the quarantine attribute is never set on this download path, Gatekeeper's signature check never fires regardless of whether Bun's binary happens to carry a real signature, so this is a lower-priority unknown than it first appears, but it's still worth confirming Bun isn't flagged by on-execution malware scanning (XProtect), which is separate from the quarantine-triggered Gatekeeper check and can run regardless of quarantine status.

### Installing packages without the npm CLI

Bun ships an npm-compatible package manager. Bun's own docs state `bun install` is a "Node.js-compatible replacement for npm" that works directly in any project with a `package.json`, accepts the same flags npm/Yarn/pnpm scripts already use "so that a command line written for npm, Yarn or pnpm keeps working," and talks to the npm registry (`https://registry.npmjs.org`) by default ([Bun docs, Install](https://bun.com/docs/cli/install)). This confirms `docs/extensions.md`'s existing `voz install npm:voz-jira` design is sound: Bun alone, with no separate npm CLI install, can resolve and fetch real npm packages. `extension-security.md` already confirms Bun skips lifecycle scripts unless explicitly trusted, and `docs/extensions.md` states voz never runs install scripts, consistent with this.

### npm registry tarball shape and search API, confirmed empirically

Fetching `https://registry.npmjs.org/lodash` directly and reading `dist-tags.latest` and `versions[latest].dist.tarball` returns: `https://registry.npmjs.org/lodash/-/lodash-4.18.1.tgz`. This confirms the documented tarball URL shape is `registry.npmjs.org/<name>/-/<name>-<version>.tgz` for unscoped packages (scoped packages follow `@scope/name/-/name-version.tgz` by the same convention, not independently re-verified here but consistent with widely mirrored tooling such as `get-npm-tarball-url`). The correct way to get this URL for any package is to read it out of the package's own registry metadata (`dist.tarball`), not to construct it by hand, since the registry is the source of truth for the exact path.

The search endpoint was also tested directly: `curl "https://registry.npmjs.org/-/v1/search?text=keywords:voz-package&size=5"` returns a well-formed, unauthenticated JSON response with an empty `objects` array (no packages carry that keyword yet, as expected, since voz has no extensions ecosystem yet). This confirms, as a primary, directly-observed result rather than a secondary summary: the `keywords:<word>` qualifier works, the endpoint needs no auth or API key for a basic text search, and the response shape (`objects`, `total`, `time`) matches what `extension-security.md`'s "Later, for a marketplace" section already assumes ("a gallery that lists npm packages with the `voz-package` keyword, like pi"). That design is directly buildable today with zero new infrastructure: an in-app panel can call this exact URL.

### A one-click install UI inside a native Swift panel

Given the above, a fully no-terminal extension install flow is mechanically straightforward for voz to build: a Swift panel row (voz already has `PanelRow`/`PanelGroup` primitives per `Sources/Voz/Menu/PanelComponents.swift` and `SetupPage.swift`'s own usage) that calls the npm search API for `keywords:voz-package`, lists results, and on tap, shells out to the existing `voz install npm:<name>` logic that `docs/extensions.md` already documents, no new install mechanism needed, only a new UI surface calling code that already exists. This avoids ever showing the user a terminal.

### Custom URL scheme risk

A `voz://install?pkg=...` URL scheme, registered via `CFBundleURLTypes` in `Info.plist`, would let any website's "Install for voz" button trigger an install without the user visiting voz directly. The risk is real and specific: **any webpage, ad, or malicious link can invoke this scheme if voz is installed**, since macOS URL scheme handlers don't restrict which site or process can open them. This is a known general weakness, not something unique to voz; it's the same class of risk as any registered custom URL scheme on macOS (`vscode://`, `slack://`, etc., all share it). Mitigation, if voz builds this: show a confirmation panel naming the exact package before installing (never auto-install silently from a URL), and treat the URL-triggered install path through the identical `--ignore-scripts`, pinned-version, warning-on-install logic `extension-security.md` already mandates for the CLI path, the URL scheme should be a UI convenience for reaching the install confirmation screen, not a bypass of it.

## Recommended path for voz

Assumes voz stays unsigned or self-signed (no $99/year Developer ID) for this flow. Click/step counts are for a non-technical user with no Terminal use except where explicitly noted.

**Install (first run), cost: one unavoidable Gatekeeper detour**

1. User clicks a download link on voz's website. Browser downloads the zip/dmg (quarantined, per `distribution.md`).
2. User opens the dmg/zip and drags voz.app to Applications (clears App Translocation, per `distribution.md`).
3. User double-clicks voz.app. Gatekeeper blocks it ("cannot verify the developer").
4. User opens System Settings > Privacy & Security, scrolls down, clicks "Open Anyway" (confirmed exact flow in section 1 of `distribution.md`, re-confirmed against Apple's own support article directly in this research: Open System Settings, click Privacy & Security, scroll, click Open Anyway, confirm Open in the reappearing prompt).
5. User double-clicks voz.app again. It opens.

That's 2 app-launch attempts and a detour through one Settings pane, roughly 5 total clicks/double-clicks from download to first successful launch. This cannot be reduced further without Developer ID and notarization; `distribution.md` already states this and this research found nothing to revise it. Every later launch (and every Sparkle update) needs none of this again, this is a one-time cost per machine.

**Onboarding (first launch to first dictation)**

6. voz's existing `SetupPage.swift` flow: three permission rows (Microphone, Accessibility, Input Monitoring), each a single click to either grant directly (Microphone, if `notDetermined`) or jump to the right System Settings pane and toggle the switch (Accessibility, Input Monitoring, both of which cannot be granted by API alone, per section 1 above, consistent with what `SetupModel.swift` already does for all three). That's roughly 3 clicks in voz plus 3 toggles in System Settings, 6 actions total, matching the "three permissions" framing already in `SetupPage.swift`'s own copy.
7. User picks a language (1 click) and leaves analytics as the shipped default (0 clicks) and clicks Done.
8. User dictates. voz downloads its speech model on first use if not already bundled (no click; this is outside this research's scope, see `docs/plan.md`/`docs/design.md` for model handling).

This matches Superwhisper's and OpenWhispr's documented onboarding shape (section 1 above); voz's existing implementation is already consistent with the best observed real-world pattern, no changes needed here.

**First extension install, fully free, fully no-terminal (requires the one-click panel this research recommends building)**

9. User opens voz's popover, goes to an "Extensions" or "Install" panel (not yet built, is a recommended addition, see section 3).
10. Panel calls `https://registry.npmjs.org/-/v1/search?text=keywords:voz-package`, already confirmed live and working with no auth needed, lists results.
11. User taps one result. A confirmation screen names the exact package (mitigating the blind-install risk from the URL-scheme discussion in section 3, applies here too even without a URL scheme, since any one-click install UI should confirm before installing a package the user didn't type themselves).
12. voz runs the existing `voz install npm:<name>` logic in the background (Bun resolves and fetches from the npm registry directly, no npm CLI needed, confirmed in section 3; `--ignore-scripts` and the on-install warning already apply per `extension-security.md`).

That's 3 taps, zero terminal use, assuming the one-click panel UI is built; today, `docs/extensions.md` requires the terminal command `voz install npm:voz-jira` instead, which is the one non-technical-user gap this research found in the current extensions design.

**What is fully free (no Developer ID, no cost)**

- The entire onboarding flow (step 6-8) and the entire extensions mechanism (Bun download, npm install, npm search/discovery) are already free and need no Apple Developer Program membership, confirmed directly in this research (Bun's own download path avoids quarantine entirely; the npm registry's search and tarball endpoints need no auth).
- A self-signed, consistently-reused signing identity (what voz already does) keeps Sparkle updates silent and TCC grants stable across updates in the common case, pending the one open question in section 1 (whether a self-signed cert's DR is stable the way a Developer ID cert's is). If that question resolves "yes," the entire update loop (step onward from first install) is also already as good as it can get for free.

**What specifically remains impossible or degraded without the $99/year Developer ID Program**

- The first-launch Gatekeeper detour (steps 3-5 above) cannot be removed, only worked around with a documented Terminal command (`xattr -cr`, per `distribution.md`) as a faster but less trustworthy alternative. This is a hard Apple platform limit, not a voz engineering gap; `distribution.md` already states this and this research found no way around it.
- Homebrew distribution through the official tap is closed off entirely as of the already-passed September 1, 2026 deadline (re-confirmed in this research with a live, dated example), so "install via `brew install --cask voz`" cannot be the free-tier answer; it was never going to be, per `distribution.md`, but this research closes the "maybe it's not enforced yet" possibility definitively given today's date.
- If the open question in section 1 resolves "no" (self-signed certs still fall back to cdhash matching), then every voz release, even without a signing-identity change, would re-prompt for all three permissions on every update, a materially worse experience than Developer ID's "grants survive updates" property, and would need to be weighed against `docs/releasing.md`'s own "never break production" framing before shipping any update at all.

## Open questions

1. **Does a stable self-signed certificate give TCC a non-cdhash, stable designated requirement?** No primary or credible secondary source found either confirming or denying this. This is the single highest-leverage unresolved question in this file: if yes, voz may already have solved the "TCC resets every update" problem for free, today, with its existing self-signed "voz Dev" identity. If no, every voz update already re-prompts for all three permissions regardless of Developer ID status, which would be a serious, currently-undocumented UX problem. Needs an empirical test on a real Mac: build two different versions with the same self-signed identity, install one, grant all three permissions, install the update, and observe whether macOS re-prompts.

2. **Is Bun's macOS release binary itself signed or notarized by Oven?** Not confirmed; Bun's GitHub Releases asset list did not load in this research's fetch, and no Bun documentation page on macOS code signing was found. Lower-urgency than it looks, since voz's download path never sets quarantine regardless, but worth a direct `codesign -dv --verbose=4` check on a downloaded Bun binary to rule out any separate XProtect flagging.

3. **Do CGRequestListenEventAccess()'s known list-registration gaps (reported on Apple's own developer forums for macOS 15) still affect macOS 26?** The only source found is an unresolved developer forum thread with no confirmed fix from Apple staff. Needs either a newer forum thread specific to macOS 26, or empirical testing on a Tahoe machine.

4. **What do VoiceInk, OpenSuperWhisper, and Handy actually show users on first launch, specifically for permissions and any Gatekeeper workaround instructions?** No README, docs site, or support page was found for any of the three describing this. `update-and-test.md` already confirmed VoiceInk signs and notarizes before publishing (implying it may not face this problem at all), but did not check its onboarding UI. Needs a direct look at each app's shipped build or a clearer public doc page than this research's searches surfaced.

5. **Does `brew upgrade` on an already-installed, already-quarantine-exempted cask re-trigger quarantine the same way a fresh `brew install` does?** Moot in practice since the official tap already excludes unsigned casks, but left open since a third-party tap was still floated as a theoretical option in `distribution.md`. No primary source found distinguishing upgrade-path from install-path quarantine behavior in Homebrew's own code or docs.

6. **Does `codesign --sign - --requirements '=designated => identifier "..."'` actually give an ad-hoc signature a TCC-stable identity the way question 1 asks for a self-signed certificate?** Found only in a single secondary source with no primary confirmation. If this works, it would be an even cheaper fallback than voz's current self-signed-certificate approach. Needs empirical testing; flagged separately from question 1 because it's a different signing mechanism (ad-hoc plus explicit requirement string, versus a real self-signed leaf certificate).
