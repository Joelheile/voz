# Update and test workflow research

Date: 2026-10-17. Target: voz's release pipeline (`docs/releasing.md`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `scripts/make-app.sh`, `scripts/package-release.sh`, `scripts/appcast.py`, `scripts/test.sh`) and Swift Testing suite (`Tests/VozCoreTests`, 221 tests on `VozCore`).

This file does not repeat `speed.md`, `stack.md`, `plugins.md`, or `notch-animation.md`.

Current state, confirmed by reading the repo: voz is an `LSUIElement` SwiftUI menu bar app built with Swift Package Manager, no Xcode project. `scripts/make-app.sh` assembles `build/voz.app` by hand (copy binary, copy Sparkle.framework, strip XPC/Headers/Modules, sign). Sparkle 2.10 ships via SPM. `appcast.xml` lives in the repo root and is served from `https://raw.githubusercontent.com/Joelheile/voz/main/appcast.xml`. `scripts/appcast.py` is a hand-written appcast writer, not `generate_appcast`. `scripts/package-release.sh` calls `sign_update` directly. CI (`ci.yml`) runs `scripts/test.sh` (Swift Testing over `vozPackageTests.xctest`, run through a custom `test-host`) and a release build on every PR. `release.yml` runs on every push to `main` (beta) and on `v*` tags (stable), importing a self-signed "voz Dev" identity into a temporary keychain, with an optional Developer ID notarization step gated on five secrets. There is no delta update generation, no phased rollout, no critical-update tag, and no snapshot or UI test target. `voz --render-design <dir>` (`Sources/Voz/Design/DesignRender.swift`) renders SwiftUI popover states to PNG via `NSHostingView` + `cacheDisplay(in:to:)`, headlessly, for human inspection only, nothing diffs the output today.

## 1. Sparkle 2

### generate_appcast vs the custom appcast.py

Sparkle's own publishing guide treats `generate_appcast` as the default path: point it at a folder of update archives (optionally with matching `.html`/`.md` release-notes files) and it builds the appcast, signs every entry with EdDSA, and writes `.delta` binary-diff files, all in one step [1]. Hand-writing the appcast is explicitly discouraged ("Writing the appcast by hand is possible but not recommended") [1].

voz's `scripts/appcast.py` reimplements a slice of this: it signs with `sign_update` in `scripts/package-release.sh`, then hand-builds the `<item>` XML and prunes to 10 entries per channel [confirmed by reading `scripts/appcast.py` and `scripts/package-release.sh`]. It does not generate deltas, and because it never runs `generate_appcast` over a directory of historical archives, it can't retroactively diff against old releases even if it wanted to, `generate_appcast` needs the actual old and new binaries on disk to build a delta [2].

VoiceInk's `scripts/release.sh`, a real competing dictation app's release script, takes the opposite approach: it finds `generate_appcast` inside Xcode's `DerivedData` SPM artifact cache and calls it directly against a working directory containing the new DMG and release notes, then cross-checks the tool's own output (version, length, signature) against the Info.plist it just built, before failing loudly on any mismatch [3]. That pattern, generate, then verify the generated appcast fields against ground truth, is worth copying regardless of whether voz keeps its own appcast writer.

**Recommendation:** voz's `Package.resolved` already pins Sparkle, so `generate_appcast` ships in `.build/artifacts/sparkle/Sparkle/bin/` (the same path `docs/releasing.md` already references for `generate_keys`). Switching `scripts/appcast.py` for `generate_appcast` would mean keeping a working copy of every release archive instead of just the `.xml`, which is a bigger change than it looks. Keep the custom script short-term; adopt `generate_appcast` only together with delta updates (next section), since that's the thing it actually buys you.

### Delta updates

Sparkle computes deltas from the real old and new app bundles with `BinaryDelta create`, verifies them with `BinaryDelta apply`, and `generate_appcast` wraps both steps automatically, writing `<sparkle:deltas>` entries with `deltaFrom`, `length`, and `sparkle:edSignature` per delta [4]. A delta is skipped if the user's installed `Sparkle.framework` has had its locales or architecture slices stripped in a way the delta can't account for (Sparkle 2.3+ attributes `sparkle:deltaFromSparkleExecutableSize`/`deltaFromSparkleLocales`), and a corrupted or non-matching delta always falls back to a full download since Sparkle checksums the result after patching [4]. voz's `make-app.sh` strips Sparkle's `XPCServices`, `Headers`, `PrivateHeaders`, `Modules`, and non-English/German `.lproj` directories from every build, consistently, so every release should produce comparable "signature" metadata, but this hasn't been verified against Sparkle's delta-skip heuristics.

Given voz prunes non-`Base`/`de` locales identically every build, deltas should apply cleanly between any two voz releases. The win is purely bandwidth: with FluidAudio and other ML dependencies linked in, `voz.app` is unlikely to be small, and full-download updates matter more as the app grows.

**Recommendation:** adopt deltas only alongside `generate_appcast` (see above), Sparkle doesn't expose delta generation as a standalone step from a hand-rolled script. Low priority: it needs an archive of every prior release's `.app` kept around (voz's CI currently only keeps the final `.zip` as a GitHub Release asset, which would need re-expanding).

### Phased rollout

`sparkle:phasedRolloutInterval` (seconds) staggers an update across Sparkle's seven hardcoded rollout groups, one group becoming eligible per interval after the item's `<pubDate>`; the group ID is cached in `SUUpdateGroupIdentifier` in user defaults, and phased rollout doesn't apply to critical updates or a manual "Check for Updates…" click [5]. This is a single extra XML attribute `scripts/appcast.py`'s `build_item` doesn't currently emit.

**Recommendation:** worth adding once voz has any track record of a bad beta reaching 100% of users immediately. Effort: small (one new attribute, one function parameter). Risk: low, degrades gracefully to "instant rollout" if unset, which is the current behavior.

### Critical updates

The top-level `<sparkle:criticalUpdate>` tag (Sparkle 2) marks a release the user can't skip and that Sparkle surfaces more eagerly; an optional `sparkle:version` attribute scopes it to installs below a given version [6]. voz's beta channel already separates risk somewhat (`<sparkle:channel>beta</sparkle:channel>`), but there's no mechanism today to force an update on users running a badly broken build.

**Recommendation:** add `--critical` as an opt-in flag to `scripts/appcast.py`'s invocation, wired from a manual workflow_dispatch input on `release.yml`. Effort: small. Risk: low, but only useful if someone remembers to use it during an actual incident, document it in `docs/releasing.md` once added.

### Channels

Sparkle's `allowedChannels(for:)` delegate (already implemented in `Sources/Voz/Updates/Updater.swift`, returning `[UpdateChannel.beta.rawValue]` when `settings.receiveBetaUpdates` is on) is exactly the mechanism Sparkle's docs describe [7]. Two caveats from the docs that aren't obviously handled in voz's code: an updater can never exclude itself from the unlabeled default channel, so there's no way to make "stable" opt-in, and the feature requires the user's installed Sparkle to be new enough (channel support shipped June 27, 2021) [7], which is moot since voz always ships its own bundled Sparkle.framework. Channels are meant for "branching off temporary updates, not parallel release tracks" [7], voz's beta/stable split is a reasonable use within that intent, but anything fancier (e.g., a third "canary" channel) should be read as against the grain of the feature.

### minimumSystemVersion

`scripts/appcast.py` already emits `<sparkle:minimumSystemVersion>26.0</sparkle:minimumSystemVersion>` unconditionally. That's consistent with `Package.swift`'s `platforms: [.macOS("26.0")]`. Sparkle 2.9+ also supports `sparkle:hardwareRequirements` to gate Apple Silicon only [5], irrelevant for voz unless an Intel build ever ships, which this research doesn't assume.

### Release notes

Sparkle supports a linked `<sparkle:releaseNotesLink>` (localizable via `xml:lang`), embedded HTML/Markdown/plain-text inside `<description>` (Markdown needs Sparkle 2.9+ and macOS 12), and a separate `<sparkle:fullReleaseNotesLink>` for changelog history [8]. voz's `release.yml` passes `--generate-notes` to `gh release create` for stable and a fixed string for beta, but `scripts/appcast.py`'s `build_item` never writes a `<description>` or `<sparkle:releaseNotesLink>`, the appcast item only has a `<link>` to the GitHub Release page. Sparkle's standard UI renders whatever's in the GitHub Release page link as a clickable link, not inline, so users checking for updates from the popover see no changelog without leaving the app.

**Recommendation:** have `package-release.sh` pass the GitHub Release notes (or a short summary) through to `appcast.py` as `<description>` with `sparkle:format="markdown"`. Effort: small-medium, needs the notes text available before the appcast step, which today runs before `gh release create`. Risk: low.

### Appcast hosting: raw.githubusercontent vs GitHub Pages

Community reports (not an official GitHub statement, flagging this explicitly as unverified) describe `raw.githubusercontent.com` sitting behind a cache that Cache-Control headers don't fully control: a 2021 issue measured a hard 300-second floor, while a GitHub Community discussion from the same era reports some repos serving `max-age=86400` (24 hours) and real-world staleness of 6–14 hours after a commit [9][10]. Because `release.yml` commits the updated `appcast.xml` straight to `main` and voz's `SUFeedURL` presumably points at the raw URL (confirmed pattern from `docs/releasing.md`'s "Check a release by hand" `curl`), a user's "Check for Updates…" click could read a stale appcast for anywhere from minutes to the better part of a day.

Real-world comparison: CodeEdit publishes its appcast via a dedicated `appcast.yml` workflow that builds a Jekyll site and deploys it to the `gh-pages` branch with `github-pages-deploy-action` [11], i.e., GitHub Pages, not raw file serving. VoiceInk's `release.sh` validates that its app's `SUFeedURL` is exactly `https://beingpax.github.io/VoiceInk/appcast.xml` before it will proceed [3], also GitHub Pages. Neither of two real Sparkle-based macOS apps surveyed here uses `raw.githubusercontent.com` for the live feed.

**Recommendation:** move the appcast to GitHub Pages (a `gh-pages` branch or a Pages-enabled `docs/` folder), fronted by GitHub's own CDN with documented, predictable caching, rather than relying on the undocumented raw-content cache. Effort: medium, needs a Pages-publishing step in `release.yml` (or a second lightweight workflow like CodeEdit's) and an `SUFeedURL` change in `Resources/Info.plist`, which is itself a user-facing risk (see Priorities, below) since changing the feed URL on an already-shipped build means that build can never discover updates on the new URL. Needs the old raw-hosted `appcast.xml` kept live and updated for some transition window, or a redirect.

### Update UX for LSUIElement apps

Sparkle 2.2+'s `SPUStandardUserDriverDelegate` exists specifically for "backgrounded applications (apps that do not appear in the Dock)" [12], exactly voz's `LSUIElement` situation. Key points from Sparkle's own gentle-reminders doc:

- By default Sparkle won't let a scheduled update alert steal focus from whatever the user is doing, except right after launch [12].
- Without implementing `supportsGentleScheduledUpdateReminders`, Sparkle logs a warning for background apps [12], worth checking whether voz's Console.app logs already show this, since `Updater.swift` doesn't currently implement any `SPUStandardUserDriverDelegate` methods, only `SPUUpdaterDelegate`.
- Sparkle's own suggested pattern for a dockless menu-bar app: add a "Check for Updates…" menu entry (voz has one via `PopoverModel`/`StatusItemController`, not verified against Sparkle's exact wiring in this pass), switch `NSApp.activationPolicy` to `.regular` only while an update is pending so a Dock badge is visible, request notification permission inside `updater(_:willScheduleUpdateCheckAfterDelay:)`, and return to `.accessory` once the user acts [12]. Sparkle's docs are explicit that push notifications "may not be delivered or seen" and recommends this only for apps users might never reactivate otherwise [12], voz, being an always-running menu bar utility the user actively invokes via hotkey, is arguably a better fit for a quieter in-popover reminder than for the Dock-badge-plus-notification pattern.

**Recommendation:** implement `supportsGentleScheduledUpdateReminders -> true` and surface "Update available" as a state in the existing popover (there's already a `ModelStatusLabel.swift` and popover state machine to extend) instead of OS notifications. Effort: medium, touches `Updater.swift`, `PopoverModel.swift`, and the design system. Risk: low; this is additive UI, no existing path breaks.

### Automatic background install

Sparkle silently downloads and installs updates after the app quits, scheduled via `SUScheduledCheckInterval`, but Sparkle "must be able to present updates to the user even if updates are set to automatically download", it still shows an alert if the app hasn't quit in a long time (`SUScheduledImpatientCheckInterval`), if installation needs authorization because of write permissions, or if the update is critical/informational [12]. voz's `updaterWillRelaunchApplication` delegate method already calls `LaunchAgent.bootOut()` before Sparkle relaunches, confirmed in `Sources/Voz/Updates/Updater.swift`, which matters precisely because of the self-signed-identity launchd binding issue documented in `docs/releasing.md`. Nothing in Sparkle's docs changes that calculus; it's a macOS launchd behavior, not a Sparkle one. No further Sparkle-side change recommended here beyond what's already implemented.

## 2. Developer ID, notarization, and CI signing

### notarytool: API key vs app-specific password

Apple's own notarization-workflow doc shows `notarytool submit` taking either `--apple-id`/`--password`/`--team-id` (requiring an app-specific password, since 2FA is mandatory on all accounts) or a `--keychain-profile` reference to credentials stored once via `notarytool store-credentials` [13]. The migration technote TN3147 documents the third option explicitly: an App Store Connect API key via `--issuer`/`--key-id`/`--key <path-to-.p8>`, with the note "There's no need to supply your Apple ID because `notarytool` works that out based on the issuer" [14].

voz's `release.yml` and `docs/releasing.md` use the app-specific-password form (`APPLE_ID`, `APPLE_APP_PASSWORD`, `APPLE_TEAM_ID`) [confirmed by reading both files]. That's the same form Stats (`exelban/stats`) uses in its real CI workflow [15] and the same form VoiceInk's local `release.sh` validates via `notarytool history --keychain-profile` before running [3]. API keys are scoped and revocable without touching a personal Apple ID password, and TN3147 recommends them for automation generally [14], but no survey repo actually uses them in CI, every real example found uses the app-specific-password/Apple-ID form. **This means voz's current choice matches observed practice, not just a theoretical "simpler path."** No change recommended; if anything, a future improvement would be migrating to an API key for the same reason TN3147 gives (revocable, no password rotation), but this is optional hardening, not a gap.

### Temp keychain pattern

voz's `release.yml` creates `${{ runner.temp }}/voz.keychain-db`, imports the signing identity via `scripts/import-signing-identity.sh` (`security create-keychain`, `set-keychain-settings -lut 21600`, `list-keychains -s`, `import … -T /usr/bin/codesign -T /usr/bin/security`, `set-key-partition-list`), and deletes the keychain in an `if: always()` step. This is the standard pattern; Apple doesn't document a CI-specific keychain recipe directly, but the steps match the generic `security` command sequence used industry-wide (and match what `Apple-Actions/import-codesign-certs`, used by Stats's workflow [15], does internally). No gap found here.

### Signing order: Sparkle framework, XPC services, Autoupdate, Updater.app

Sparkle's sandboxing doc shows manual re-signing in this order: `Installer.xpc`, then `Downloader.xpc` (with `--preserve-metadata=entitlements` on Sparkle 2.6+, since Downloader needs the app's own network entitlements), then `Autoupdate`, then `Updater.app`, and finally `Sparkle.framework` itself, with an explicit warning never to add `--deep` to any custom signing script, since that can resign nested code incorrectly [16]. `scripts/make-app.sh`'s comment already cites this exact page and follows the order for the two pieces voz ships (`Autoupdate`, `Updater.app`, then the framework), voz's `make-app.sh` deletes `XPCServices` outright rather than signing it, which is consistent with voz not using Sparkle's sandboxed/XPC-based installation (XPC services are for App Store sandboxed Sparkle installs, which voz, as a non-Mac-App-Store app, doesn't need) [17]. No gap found; the current script matches documented practice for a non-sandboxed Sparkle integration.

### Hardened runtime

voz signs with `--options runtime` in `make-app.sh`, matching Apple's explicit requirement that notarized software use the hardened runtime with a secure timestamp [18]. Confirmed consistent.

### Can disable-library-validation go?

`com.apple.security.cs.disable-library-validation` exists because the self-signed "voz Dev" identity has no team ID, and macOS's library validation (part of the hardened runtime) only accepts frameworks signed by Apple or by the exact same team ID as the main executable [confirmed by reading `docs/releasing.md` and `Resources/voz.entitlements`]. Sparkle's own docs don't mention this entitlement directly, but the underlying rule is Apple's, not Sparkle's: once voz and the bundled `Sparkle.framework` are both signed by a real Developer ID (which carries a team ID), library validation passes without the entitlement, which is exactly what `docs/releasing.md` already says, and what this research confirms independently from Apple's hardened-runtime model. No new finding beyond what's already documented; the entitlement removal is correctly gated on migrating off the self-signed identity, not on anything Sparkle-specific.

### Why TCC grants survive updates only with a stable designated requirement

A code signing designated requirement (DR) is what macOS checks to decide whether an updated binary is "the same app" as the one the user already granted microphone/Accessibility/Input Monitoring access to. `codesign -d -r-` prints it; a typical Developer ID DR pins the bundle identifier and the certificate's team ID (`certificate leaf[subject.OU] = "TEAMID1234"`) [confirmed via `codesign` man-page-level behavior, general knowledge, Apple's "Resolving common notarization issues" page covers DRs but this research's fetch of that specific page returned only its title, so treat this paragraph's specifics as unverified against that exact page]. Practically: TCC grants key off the DR, so as long as every release is signed by the same identity, `CFBundleIdentifier` doesn't change, and the DR therefore doesn't change, updates keep existing grants. voz's `docs/releasing.md` already states this correctly ("macOS keeps microphone and Accessibility permissions across updates only when the signing identity stays the same" and "the signing identity changes [after adding Developer ID], so macOS asks every user … again after the first notarized update"), this research corroborates that claim's mechanism but could not independently re-verify it against Apple's own DR documentation in this pass due to a fetch failure; flagging as the one claim in this section not confirmed against a primary source that actually returned content.

### Migration cost: self-signed to Developer ID

`docs/releasing.md` already lays out the real cost accurately: a one-time permission re-prompt for every user (microphone, Accessibility, Input Monitoring) and a launchd re-registration hiccup (`docs/releasing.md`'s existing note that "launchd binds the agent to the signature of the registered binary" under a self-signed, team-ID-less identity, and "can refuse to start the new binary" after an update) [confirmed by reading `docs/releasing.md`]. This matches Apple's general model: `SMAppService` launch agents are, like TCC, tied to code identity, and a self-signed identity with no team ID is inherently less stable across rebuilds than a Developer ID cert reused release after release. No new finding; voz's docs already capture this correctly. The one actionable gap: there's no recorded verification step for this migration beyond "verify it with `kill -9`", see the post-release smoke-check recommendations below for a scriptable replacement.

## 3. Testing

### Swift Testing fit

Apple's Swift Testing framework page states it "integrates seamlessly with Swift Package Manager testing workflow" [19], directly relevant since voz has no Xcode project. `@Test`, `@Suite`, and parameterized tests run in parallel by default, with `.serialized` available for suites that share external state [19]. voz already uses this for all 221 `VozCoreTests` tests via `swift build --build-tests` plus a custom `test-host` binary (`scripts/test.sh`) that links the Command Line Tools' XCTest-adjacent `Frameworks` directory to make the `.xctest` bundle runnable outside Xcode, this is a known, if unusual, pattern for SPM-only macOS Swift Testing without Xcode, and matches the framework's stated SPM-first design.

### Snapshot testing with swift-snapshot-testing

pointfreeco's library implements exactly the primitive voz's `DesignRender.swift` already hand-rolls: `Snapshotting<NSView, NSImage>.image` calls `view.bitmapImageRepForCachingDisplay(in:)` and `view.cacheDisplay(in:to:)` to rasterize an `NSView` (confirmed by reading `Sources/SnapshotTesting/Snapshotting/NSView.swift` in the cloned repo at commit HEAD on 2026-10-17) [20], the same AppKit APIs `DesignRender.swift`'s `write(_:to:name:appearance:)` uses directly. On first run a snapshot is recorded to a `__Snapshots__` folder next to the test and the test fails with the file path; later runs diff against that reference, with failures attaching an image diff visible in Xcode's Report Navigator; re-recording is explicit (`withSnapshotTesting(record: .all)` or a `.snapshots(record: .failed)` suite trait) rather than automatic [21]. The library documents comparing snapshots "on the same simulator" that recorded them for iOS; for macOS the equivalent caveat is almost certainly OS version and GPU/font-rendering, not confirmed against a primary source for macOS specifically, flagging as inferred from the iOS guidance.

**Could `--render-design` become a CI snapshot regression test?** Mechanically, yes, `DesignRender.run` already does everything `Snapshotting<NSView, NSImage>.image` does by hand (`NSHostingView`, `cacheDisplay(in:to:)`, PNG write), just without a stored reference or a pass/fail comparison. The real question is where references get committed and compared: Xcode's Report Navigator UI for inspecting diffs (the normal `swift-snapshot-testing` workflow) doesn't exist outside Xcode, so a headless `swift test` run in CI would need to fail loudly on pixel mismatch and dump both images as CI artifacts for a human to look at, swift-snapshot-testing's `.image` strategy's `assertSnapshot` does fail with a readable message and can attach the diff as an XCTest attachment even without Xcode's UI, so this is achievable, just less convenient to review than in Xcode.

**Recommendation:** convert `DesignRender`'s per-state renders into a `VozCoreTests`-adjacent snapshot test target using `swift-snapshot-testing`, keeping `--render-design` itself as the human-inspection CLI entry point (useful for visually reviewing a change before committing new reference snapshots) and adding a `swiftSnapshotTesting` dependency plus a small test file that calls the same `Fixture`/`popoverStates` data `DesignRender.swift` already has. Effort: medium, needs the new SPM dependency, a `VozTests` target that can import `Voz`'s internal types (currently only `VozCoreTests` exists, testing `VozCore`; `Voz` is an `executableTarget`, which complicates testability, may need to extract the popover views or move `Fixture` into a shared location, or add a new test target with `@testable import Voz`, which SPM supports for executable targets in recent toolchains, not independently verified in this pass). Risk: medium, font rendering, dark/light appearance toggling, and `@MainActor` isolation in `DesignRender.swift` are all plausible sources of CI flakiness that would need investigation before trusting the gate.

### UI testing a menu bar app without an Xcode project

Maccy (`p0deje/Maccy`), a real production menu bar clipboard manager (it does have an `.xcodeproj`, unlike voz), ships a full XCUITest suite in `MaccyUITests/MaccyUITests.swift`: it instantiates `XCUIApplication()` directly and queries `app.descendants(matching: .any).matching(identifier: "copy-history-item")` against the popover's contents, so XCUITest's accessibility-tree-based element queries clearly work against a backgrounded/accessory-policy app's popover UI, not just Dock-visible windows [22]. This is strong evidence against any assumption that `LSUIElement` apps can't be UI-tested with standard XCUITest.

The catch for voz specifically: XCUITest is an Xcode/XCTest feature tied to an Xcode scheme and test plan (`Maccy.xctestplan` exists in that repo) [confirmed: `p0deje/Maccy` root listing includes `Maccy.xctestplan`], and voz has deliberately avoided an Xcode project in favor of pure SPM. `swift test` can run XCTest-based UI test targets from SPM in principle (XCTest fully supports SPM test targets on macOS), but `XCUIApplication` launching a built `.app` bundle rather than an in-process test host is a different mechanical story than voz's current `vozPackageTests.xctest` + custom `test-host` pattern, and this research did not find a primary-source example of XCUITest driving an SPM-packaged (no `.xcodeproj`) macOS app. Call this an open question requiring a small spike, not a confirmed yes.

**Recommendation:** spike a single XCUITest target added to `Package.swift` that launches `build/voz.app` (already built by `make-app.sh`) via `XCUIApplication(bundleIdentifier:)` or a direct path launch, and asserts on one trivial thing (e.g., the status bar item exists). If `swift test` can drive it the same way `scripts/test.sh` drives the current host, expand coverage; if not, this becomes a CI-only concern requiring `xcodebuild test` against a generated scheme, which is a much bigger ask given voz's explicit no-Xcode-project stance. Effort: medium to find out, potentially large to adopt fully. Risk: low for the spike itself (additive), but don't commit to broad UI test coverage before confirming the mechanics work outside Xcode.

### Testing permission flows

Apple's own `tccutil` man page (confirmed by running `man tccutil` locally, this is Apple's shipped documentation, not a third-party source) documents exactly one capability: `tccutil reset <service> [bundle_id]`, which "reset[s] all decisions for the specified service, causing apps to prompt again the next time they access the service" [23]. This is scriptable (`tccutil reset Microphone com.joelheile.voz`, `tccutil reset Accessibility com.joelheile.voz`) for local manual testing of voz's permission-request flow, but it requires the invoking process to itself have, or be run under, sufficient privilege, and GitHub's hosted `macos-26` runner is unlikely to grant a CI job the TCC prompts or Accessibility/Input Monitoring grants voz needs to actually exercise end-to-end (GitHub Actions' macOS runners are headless and don't have a logged-in user clicking "Allow" on a system prompt), this is a reasonable inference, not confirmed against GitHub's own runner documentation in this pass. **CI cannot test real permission-grant UX for voz.** Keep this as a manual, documented pre-release checklist step using `tccutil reset`, not a CI gate.

### End-to-end update test via local HTTP server

No primary source found describing Sparkle-specific local-HTTP-server testing beyond Sparkle's own "Test Sparkle out" step, which recommends a simpler approach: lower `CFBundleVersion` on a dev build (or host a separate high-version "stub" build on an alternate feed), delete `SULastCheckTime` from the bundle's defaults to force an immediate check, run a manual "Check for Updates…", and watch Console.app for the actual update/signature verification logs [24]. Sparkle's doc explicitly flags that Sparkle won't even ask the user about automatic checks until the second launch of a build, which is an easy thing to misread as a bug during manual testing [24].

For a scripted, repeatable version of this: point `SUFeedURL` at `http://127.0.0.1:<port>/appcast.xml` (Sparkle doesn't require HTTPS for the feed itself, only recommends it for production, not independently confirmed, inferred from `App Transport Security` being a documented, separately-configurable topic in Sparkle's docs [25] rather than a hardcoded requirement), serve a folder containing an older signed `.zip`/appcast with Python's `http.server` or similar, launch an older-versioned build of `voz.app`, trigger a check, and assert the newer bundle landed. This is buildable entirely from documented Sparkle mechanics (`SUFeedURL`, `sign_update` verification, delta checksum fallback) but this research found no example of another project scripting it exactly this way, it would be new tooling for voz, not a copy of an existing pattern.

**Recommendation:** worth building as a script (`scripts/test-update.sh`) that automates the manual steps Sparkle's docs describe, run on-demand before a stable release rather than on every CI run (it needs two full builds and real network/process launches, which is slow and somewhat flaky for a PR gate). Effort: medium. Risk: low, since it's a new script, not a change to the shipping pipeline.

### Post-release smoke checks

Real-world precedent for exactly this already exists in the surveyed repos. Stats's actual release workflow runs, in order: `codesign --verify --strict` on a nested component, a version-match assertion between the main app and a plugin, then `spctl -a -t exec -vvv build/Stats.app` as a dedicated "Verify gatekeeper" step, gated behind `if: inputs.dry_run != true` so these checks don't block a non-publishing dry run [15]. VoiceInk's `release.sh` goes further: `codesign --verify --deep --strict --verbose=2` on both the `.app` and the `.dmg`, `stapler staple` + `stapler validate` on both, `spctl -a -t exec -vv` on the app and a different `spctl -a -t open --context context:primary-signature -vv` invocation for the DMG specifically, `hdiutil verify` on the DMG, then it mounts the DMG and re-reads `CFBundleShortVersionString`/`CFBundleVersion`/`SUPublicEDKey` straight out of the mounted bundle to confirm the packaging round-tripped correctly, and finally cross-checks every field of the freshly generated appcast XML (version, short version, minimum system version, download URL, enclosure length, EdDSA signature) against the actual built artifact before calling the release done [3]. That is a materially more rigorous smoke-check suite than voz's current `codesign --verify --deep --strict "$APP"` (one line, in `make-app.sh`, with no `spctl` or appcast cross-check at all).

**Recommendation:** add to `scripts/package-release.sh` or a new post-step in `release.yml`: `spctl --assess --type execute -vv build/voz.app` (or `spctl -a -t exec`, same thing, different flag spelling, Apple's docs use `--assess`/`-a` interchangeably, both documented), an appcast field cross-check against the just-built `.zip`'s actual signature/length (mirroring VoiceInk's pattern, which is cheap since `package-release.sh` already computes `SIGNATURE` and `LENGTH` locally, just add an assertion against what `appcast.py` wrote back), and, once notarization is non-optional, `xcrun stapler validate build/voz.app`. Effort: small, these are a handful of extra shell lines using tools already present on `macos-26` runners. Risk: very low; purely additive verification that fails the release job loudly instead of shipping a broken artifact silently.

The clearest pattern across real menu bar apps: **the ones with the most mature-looking CI (CodeEdit) or the most rigorous manual process (VoiceInk) both treat signing/notarization/appcast generation as deliberately slow and verification-heavy**, not fast-and-automatic. VoiceInk's script refuses to run on a dirty git tree, refuses to proceed without a validated notary profile, and cross-checks four or five independent sources of truth (Info.plist, generated appcast, mounted DMG, Sparkle keychain key) before calling a release "prepared." CodeEdit gates its one-click pre-release dispatch behind lint and test jobs completing first. Several real apps (Ice, Maccy, Rectangle's actual build.yml) have comparatively little or no CI-side signing/notarization/appcast automation at all, this is a genuinely mixed bag, not a settled "best practice everyone does." voz's existing automated, tag-triggered, secret-gated pipeline is already more automated than half the apps surveyed here; the gap is specifically in appcast hosting, release notes, and post-build verification rigor, not in the overall "should this be automated" question.

## Prioritized changes for voz

In order. Each entry: what, effort, risk.

1. **Add post-build smoke checks to the release pipeline**: `spctl --assess` on the built `.app`, and an assertion that `appcast.py`'s written signature/length match what `package-release.sh` actually computed. Effort: small (a few shell lines in `scripts/package-release.sh` or a new step in `release.yml`). Risk: very low, purely additive, catches a broken release before it's published rather than after. Do this first; it's cheap insurance for a pipeline that already ships to real users.

2. **Add release notes to the appcast `<description>`**: pipe the `gh release create` notes (or a short summary) into `scripts/appcast.py` so Sparkle's update UI shows a changelog instead of only a link. Effort: small-medium (needs notes available before the appcast step runs; `release.yml`'s step order may need adjusting). Risk: low.

3. **Build a scripted end-to-end update test** (`scripts/test-update.sh`): older build, local HTTP-served appcast, trigger a check, assert the new bundle lands, following Sparkle's own documented manual test recipe (`SULastCheckTime` deletion, Console.app inspection) but scripted. Run on-demand before stable releases, not on every CI run. Effort: medium. Risk: low (new script; doesn't touch the shipping pipeline).

4. **Spike XCUITest against the built `.app`** to settle whether SPM-only (no `.xcodeproj`) macOS apps can run real UI tests the way Maccy does against its popover. One trivial assertion (status item exists) is enough to answer the question. Effort: medium to spike, unknown to adopt broadly depending on the answer. Risk: low for the spike; don't commit further testing investment until this returns an answer.

5. **Move the appcast off `raw.githubusercontent.com` to GitHub Pages**, matching CodeEdit and VoiceInk. Effort: medium (new publish step, `SUFeedURL` change, transition-window handling so already-shipped builds don't silently stop finding updates). Risk: medium, this is the one change here that can break updates for existing users if sequenced wrong; keep the old raw-hosted feed live and serving the latest appcast until every build in the wild that might check it has had a chance to update past the cutover, or keep both feeds in sync for a release or two.

6. **Convert `DesignRender`'s popover states into committed `swift-snapshot-testing` references** gated in CI, keeping `--render-design` as the human-inspection CLI. Effort: medium (new SPM dependency, new test target wiring against an `executableTarget`, needs `Fixture` made testable). Risk: medium, plausible flakiness from font rendering or appearance-switching; don't gate PRs on this until a trial run proves stable.

7. **Add phased rollout and a critical-update escape hatch** to `scripts/appcast.py` (`sparkle:phasedRolloutInterval`, optional `sparkle:criticalUpdate`). Effort: small. Risk: low; both are inert unless explicitly used.

8. **Implement `supportsGentleScheduledUpdateReminders` and an in-popover "update available" state** instead of relying on Sparkle's default alert behavior for a backgrounded app. Effort: medium (touches `Updater.swift` and the popover state machine). Risk: low, additive UI.

9. **Delta updates via `generate_appcast`**, once (and only once) the appcast generation itself has moved off the hand-rolled script, deltas aren't realistically addable to `appcast.py` standalone. Effort: large relative to the rest of this list (needs an archive of every prior release's unpacked `.app`, not just the final `.zip`, which changes what CI needs to retain). Risk: low once `generate_appcast` is adopted, since Sparkle checksums and falls back to a full download on any mismatch.
